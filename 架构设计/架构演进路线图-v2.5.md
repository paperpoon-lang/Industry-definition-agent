# 架构演进路线图 v2.5 — 行业定义 Agent 蓝图

> 版本：v2.5 | 日期：2026-06-12
> 定位：定义完整系统长什么样，以及从 Demo → 生产级的演进路径
> 起点：v4 Demo MVP（~760 行核心 Python）
> 终点：生产级系统（支持批量处理、多用户、成本可控、可审计）
>
> v2.5 基于 v2（2026-06-05）与阶段一多行业验证数据（2026-06-12）迭代。变更摘要：
> - 阶段二从"一张大表"重构为 A/B/C/D 四组（基于真实痛点裁剪）
> - 阶段二新增 `quality_flags` 机制（阶段一已验证的静默降级风险）
> - Output Safety（防覆盖）从阶段三提至阶段二 A 组（已验证的真实风险）
> - methodology 拆分从"8 模块"简化到"2-3 模块"
> - Circuit Breaker 从完整三态状态机简化为极简版（`asyncio.wait_for` 加超时）
> - 阶段二进入条件补充"开发者自测验证"
> - 阶段二退出条件修正为"停留在阶段二"而非"退回到阶段一"
> - `FixItem` 结构化设计只留设计笔记，阶段二不实现
> - 批处理排队策略从阶段三移除（无需求确认）
>
> **与 v2 的关系**：v2.5 是 v2 的阶段二重构版本，阶段一（无变化）、阶段三、阶段四（无本质变化）保持 v2 原样。v2 不废弃，作为参考保留。

**核心设计原则（贯穿所有阶段）**：

1. **接口向前兼容**：v4 打桩的接口（`call_with_retry` → `CircuitBreaker.call`、`SimpleLogger` → `SessionEventLog`、`save_checkpoint` → `CheckpointManager`）在升级时只换实现不换签名
2. **质量组件不减**：Evaluator 独立化、Context Builder 四层、搜索并行压缩——这三个从 v4 起就完整实现，后续阶段只增强不替换
3. **基础设施逐步完善**：从 v4 的"print 日志"到生产的"审计管道"，从 v4 的"retry"到生产的"完整 Circuit Breaker"，逐步升级
4. **演进有闸门**：每个阶段有明确的进入条件和退出条件，什么情况下不升级和什么情况下升级同样重要

## 二、演进路径：四个阶段

### 阶段一：Demo MVP（v4，现在）

**目标**：跑一次出高质量报告，给人看不尴尬。

| 维度 | 状态 |
|---|---|
| **代码量** | ~760 行核心 Python（总计 ~1,585 行含 Mock 数据和脚手架） |
| **运行方式** | `python frost_agent.py "行业名称"` |
| **Harness 组件** | 6 个完整做 + 5 个打桩 + 3 个不做 |
| **Environment** | Credential Vault (最小实现: .env) |
| **并发** | 无（单次 CLI 运行） |
| **持久化** | Checkpoint (save + load，单文件覆盖写入) |
| **审计** | print 日志 (`SimpleLogger`) |
| **成本** | 单一模型 (DeepSeek-V4-Pro via SiliconFlow)，~$0.03/次 |
| **延迟** | ~8 分钟/次（实测） |

**验收标准**：
- [x] `python frost_agent.py "低空经济物流"` 稳定产出报告（3/3 次成功）
- [x] Step 5 自检 C1-C5 逐项有 PASS/FAIL
- [x] 报告不含竞争排名/市场规模/投资建议
- [x] 自检 FAIL 时报告头部有警告标记
- [x] 崩溃后可恢复（kill -9 后重跑）
- [x] Step 1 搜索 < 10 秒
- [x] 成本/延迟有实测数据（回填到 v4 文档第五章）

**已验证行业**：低空经济物流、汽车、新能源汽车、人工智能医疗、半导体制造、生物医药

**已知局限（阶段一文档已记录）**：
1. `or` fallback 防止崩溃但产生静默降级（→ 阶段二 A 组 `quality_flags`）
2. 报告覆盖写入（→ 阶段二 A 组 Output Safety）
3. API 超时无主动中断（→ 阶段二 B 组 Circuit Breaker 极简版）
4. 无结构化日志（→ 阶段二 A 组 Session Event Log → JSONL）
5. 单文件方法论维护困难（→ 阶段二 A 组 methodology 简化拆分）

---

### 阶段二：内部试用与基础设施加固

**进入条件（闸门）**：以下全部满足方可进入阶段二：

- [x] 3 个不同行业的自检 C1-C5 全部 pass（或全部警告明确指向 LLM 能力边界）
- [ ] 单次运行端到端耗时 ≤ 120 秒（v4 实测 ~8 分钟，需验证最近运行数据）
- [ ] API 费用在可接受范围内（单次 < $0.10，v4 实测 ~$0.03）
- [ ] **开发者自测验证完成**：开发者在 1 天内跑 3-5 个行业，记录频率、耗时、痛点、成本、API 超时情况。基于自测结果决定 B 组和 C 组的范围。

**退出条件**：如果阶段二 A 组做完后，开发者自测显示需求很低（每周 < 3 次），则**停留在阶段二（A 组已完成）**，不做 B/C 组。如果阶段二运行 1 个月后，B 组和 C 组的需求仍未出现，则不进入阶段三。A 组的改进本身就是有价值的基础设施，即使使用频率低也不应退回到阶段一。

---

#### 阶段二 A 组（必须做，1-1.5 周）

已验证的痛点 + 成本极低的基础设施 + 阶段三循环的接口预留。不取决于使用模式。

| 组件 | 工作量 | 为什么必须做 | 关键设计约束 |
|------|--------|------------|-------------|
| **`quality_flags` 机制** | 0.5 天 | 阶段一真实发现的静默降级风险。`or` fallback 防止了崩溃，但让降级信息"消失在状态对象的一个字段里" | 写入 `StepOutput` 独立字段（不污染 `result`），Step 6 汇总到报告尾部。格式约定：`"{category}:{field}:{severity}"`（如 `"llm_empty_field:summary:high"`）。为阶段三循环预留**机器可读的信号** |
| **Session Event Log → JSONL** | 1 天 | 从 print 升级到 JSONL，为后续调试和审计打基础。即使只有一个开发者，结构化日志也是必需 | 按 step/type 过滤，append-only 写入，支持查询接口。签名兼容 `SimpleLogger.log()` |
| **Token Audit → 持久化** | 0.5 天 | 让成本从推测变实测。阶段二闸门条件"费用 < $0.10"需要独立审计数据 | 读取 `StepOutput.token_usage`，生成单次运行成本报表。不改变 `StepOutput` 模型 |
| **Checkpoint → 多版本 + 过期清理** | 0.5 天 | 当前覆盖写入已够用，但多版本是更安全的默认。同时为阶段三循环预留**可恢复的旧版本** | 每次 save 创建新版本文件，自动保留 7 天。签名兼容 `save_checkpoint()` |
| **Output Safety（输出安全）** | 0.5 天 | 当前阶段一的报告保存是**覆盖写入**。如果跑了两次同一个行业，第二次完全覆盖第一次。这是**真实风险，不是假设** | 文件名自动追加时间戳（如 `新能源汽车_20250612_143052_行业定义报告.md`），检测到已存在时追加版本号 |
| **methodology/ → 简化拆分** | 0.5-1 天 | 当前痛点是"方法论调整需要改代码"，不是"单文件太大"。**简化**：不是"拆成 8 模块"，而是拆成 2-3 模块 + `_meta.yaml` 版本声明 | 保持正则切片逻辑，只把最可能独立变更的章节（如 Hard Rules、Heuristics、自检清单）拆出，主文件保留框架 |

**A 组总计：约 3.5-5 天，加上调试和文档，1-1.5 周。**

---

#### 阶段二 B 组（有条件做，取决于开发者自测验证）

假设性需求，需在开发者自测验证后决定。如果自测结果不支持，全部跳过。

| 组件 | 工作量 | 触发条件 | 验证方式 |
|------|--------|---------|---------|
| **Persistent Memory (SQLite)** | 3-5 天 | 如果实际使用频率 ≥ 每天 3 个行业，或方法论规则冲突的压力测试需要跨行业对比 | 开发者自测记录：频率 |
| **Circuit Breaker（极简版）** | 0.5 天 | 如果 API 超时/卡死问题出现（阶段一曾出现 Step 4 卡死 5-10 分钟） | 开发者自测记录：API 超时情况 |

**B 组总计：如果两项都做，约 1-2 周；如果都不做，0 周。**

**关于 Circuit Breaker 的简化**：不做完整三态状态机（CLOSED/OPEN/HALF_OPEN），先用 `asyncio.wait_for` 在 `call_with_retry` 层面加超时保护。这是最低成本解决最痛"无限等待"问题的方式。如果后续 API 稳定性问题持续出现，再在阶段三升级为完整状态机。

---

#### 阶段二 C 组（可选做，取决于开发者自测验证）

体验升级，不是功能必需。如果开发者自测或实际使用者明确需要，才做。

| 组件 | 工作量 | 触发条件 | 验证方式 |
|------|--------|---------|---------|
| **Web UI (Streamlit/Gradio)** | 4-5 天 | 如果实际使用者明确反馈**"命令行不方便"**或**"需要给非技术用户展示"** | 开发者自测记录：体验 |
| **Sprint Contract (自动化协商)** | 2-3 天 | 如果 `STEP_TASKS` 的验收标准**需要频繁调整**（目前运行稳定，需求不迫切） | 开发者自测记录：是否需要调整方法论规则 |

**C 组总计：如果两项都做，约 2 周；如果都不做，0 周。**

---

#### 阶段二 D 组（明确推迟到阶段三）

| 组件 | 推迟原因 |
|------|---------|
| Model Router | 当前单一模型运行稳定，无降级需求 |
| Prompt Cache | 当前成本在可接受范围内，不需要优化 |
| API Server | 没有批量处理需求确认 |
| Rate Limiter | 没有 API 限流问题 |
| Evaluator-Optimizer 闭环 | 阶段二保持"失败时注入警告 + 人工审查"的简单契约。循环需要稳定的 Evaluator 基线 |
| Harness Ablation | A/B 测试框架，在批量处理场景下才有价值 |

### 阶段三：批量处理（生产化前奏）

> 阶段三内容基本保持 v2 不变。以下为主要升级项。

**进入条件（闸门）**：
- [ ] 阶段二稳定运行至少 1 个月，无重大故障
- [ ] 累积 ≥ 50 个行业报告，方法论附注质量持续达标
- [ ] 需要批量处理的业务需求已确认（如"季度行业扫描需跑 50 个行业"）

**退出条件**：如果批量处理的月均请求 < 10 次，不升级到阶段四。API Server 即可满足需求。

**升级项**：

| 组件 | 阶段二状态 | 阶段三升级 | 工作量 |
|---|---|---|---|
| **Model Router** | 单一模型 | 按步骤选模型（搜索用 flash，生成用 sonnet）+ fallback 降级链 | 3-4 天 |
| **Prompt Cache** | 无 | 静态 System Prompt 前缀缓存对齐，降低 40-80% 成本 | 1 天 |
| **Rate Limiter** | 无 | API 调用频率限制，防止触发供应商限流 | 0.5 天 |
| **API Server** | 无 | FastAPI：POST /analyze（单个行业）+ POST /batch（批量） | 2-3 天 |
| **Evaluator-Optimizer 闭环** | 无（人工审查后修）| 最多 3 轮自动修正（保留人工 override）。依赖阶段二的 `quality_flags` 和 Checkpoint 多版本 | 2 天 |
| **Output Safety** | 防覆盖（A 组已完成）| 完整 workspace 边界检查 | 0.5 天 |
| **Harness Ablation** | 无 | 可开关单个 harness 组件，对比质量/成本 | 1 天 |

**预计工作量**：~3-4 周（1 人）

## 三、阶段二关键新增：阶段三循环的接口预留

路线图 v2 把循环（Evaluator-Optimizer 闭环）放在**阶段三**。这个判断合理——阶段二需要先有稳定的 Evaluator 基线，循环才有可靠的停止条件。

**阶段二必须做循环的"接口预留"，不做循环本身：**

| 阶段二预留 | 为什么阶段三需要它 |
|-----------|------------------|
| **`quality_flags` 标准化格式** | 循环需要知道"失败的是哪一步"，决定重跑哪一步 |
| **Checkpoint 多版本** | 循环需要恢复到某一步的旧版本，重跑后续步骤 |
| **Step 5 `fixes_required` 设计笔记** | 循环需要读取"修复建议"，生成重跑策略 |

**预留的具体实现：**

```python
# models.py — StepOutput 中 quality_flags 的标准化格式（阶段二实现）
class StepOutput(BaseModel):
    # ... 现有字段 ...
    quality_flags: list[str] = Field(default_factory=list)
    # 格式约定："{category}:{field}:{severity}"
    # 示例："llm_empty_field:summary:high", "search_partial_failure:2/3:medium"

# Step 5 fixes_required 的结构化设计（阶段二只留设计笔记，不实现 Pydantic 模型）
# 当前 evaluator.py 的 fixes_required 保持为 list[str]
# 阶段三可基于此设计升级：
```

## 四、各阶段接口兼容性保证（含行为语义差异声明）

### 4.1 `call_with_retry()` → `CircuitBreaker.call()`（极简版）

```python
# v4 (打桩)
async def call_with_retry(fn, max_retries=2):
    for attempt in range(max_retries + 1):
        try:
            return await fn()
        except Exception:
            if attempt == max_retries: raise
            await asyncio.sleep(2 ** attempt)

# 阶段二 B 组 (极简版) —— 签名兼容，仅增加超时保护
async def call_with_retry(fn, max_retries=2, timeout_seconds=None):
    for attempt in range(max_retries + 1):
        try:
            if timeout_seconds:
                return await asyncio.wait_for(fn(), timeout=timeout_seconds)
            return await fn()
        except asyncio.TimeoutError:
            if attempt == max_retries: raise
        except Exception:
            if attempt == max_retries: raise
            await asyncio.sleep(2 ** attempt)
```

**已知行为语义差异**：
- v4: 无超时保护，API 卡死时无限等待
- 阶段二极简版: `timeout_seconds` 参数可选，默认不传保持 v4 行为兼容
- 阶段三完整版: 三态状态机（CLOSED/OPEN/HALF_OPEN），但阶段二不做

### 4.2 `SimpleLogger` → `SessionEventLog`

```python
# v4 (打桩)
class SimpleLogger:
    def log(self, event_type: str, data: dict):
        print(f"[{event_type}] {data}")

# 阶段二 A 组 (完整实现) —— 签名兼容
class SessionEventLog:
    def log(self, event_type: str, data: dict):     # 签名相同
        ...
    def query(self, event_type=None, step_id=None):  # 新增
        ...
```

**已知行为语义差异**：
- v4: `log()` 同步执行；阶段二: JSONL 文件写入，需处理 `IOError`
- v4: 输出到 stdout；阶段二: 输出到文件，stdout 需另外处理

### 4.3 `save_checkpoint` / `try_resume` → `CheckpointManager`

```python
# v4 (打桩)
def save_checkpoint(state: ReportState, step_id: str): ...
def try_resume(industry_name: str) -> ReportState | None: ...

# 阶段二 A 组 (完整实现)
class CheckpointManager:
    def save(self, state: ReportState, step_id: str): ...
    def load(self, industry_name: str) -> ReportState | None: ...
```

**已知行为语义差异**：
- v4: 单文件覆盖写入；阶段二: 多版本管理，每次 save 创建新版本文件
- v4: 无清理逻辑；阶段二: 自动过期清理（默认保留 7 天）

### 4.4 Token Audit (StepOutput 字段) → `TokenAudit`

- v4: `StepOutput.token_usage` 字典字段
- 阶段二: `TokenAudit` 类读取 `StepOutput.token_usage` 生成持久化报表
- **兼容性**：完全不破坏现有代码

| 风险 | 阶段 | 应对措施 |
|---|---|---|
| Demo 不稳定（API 超时/限流） | v4 | `call_with_retry` + 搜索全失败降级 |

## 七、附录：LangGraph 集成（可选技术探索）

（保持 v2 原文不变，仅全文见 v2）

LangGraph 的 StateGraph 在以下场景有价值：
- 步骤间出现**条件分支**（如"Step 3 决策后可能跳过 Step 4"）
- 需要**子图嵌套**（如 Step 1 内部有独立的搜索→压缩→总结 DAG）
- 需要**Human-in-the-Loop 断点重放**

**当前行业定义 Agent 的六步流程为严格线性**。用 LangGraph 替换当前的顺序 for 循环，不会带来功能增益——但会引入依赖、学习成本和调试复杂度。

**触发条件**（只有在以下需求确认时才考虑 LangGraph 集成）：
1. 方法论演进导致步骤间出现条件分支
2. 需要断点重放（非线性的 checkpoint 恢复，而非从头重跑）

**如果在阶段四引入 LangGraph**：预估工作量 5-7 天，但建议先在阶段三的 Harness Ablation 框架下做 A/B 对比（LangGraph Orchestrator vs 原生 Orchestrator），确认有实质性收益后再全量迁移。
