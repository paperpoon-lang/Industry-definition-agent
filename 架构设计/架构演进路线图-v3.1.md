**核心设计原则（贯穿所有阶段）**：

1. **接口向前兼容**：v4 打桩的接口在升级时只换实现不换签名
2. **质量组件不减**：Evaluator 独立化、Context Builder 四层、搜索并行压缩——这三个从 v4 起就完整实现
3. **基础设施逐步完善**：从 v4 的"print 日志"到生产的"审计管道"，逐步升级
4. **演进有闸门**：每个阶段有明确的进入条件和退出条件
5. **命名诚实**（v3 新增）：组件名称必须反映其实际能力。`call_with_timeout` 不叫 Circuit Breaker，因为它不会熔断

### 2.2 延迟拆解（基于代码分析）

[models.py](file:///Users/paper/trae_project/行业定义agent/demo/models.py) 第 160-185 行的 `STEP_BUDGETS` 定义了各步超时预算：

| 步骤          | timeout\_seconds | max\_tokens | LLM 调用次数 | 说明                                 |
| ----------- | ---------------- | ----------- | -------- | ---------------------------------- |
| Step 1 信息收集 | 120              | 100000      | 1        | 搜索 2-4s + LLM 总结                   |
| Step 2 维度筛选 | 60               | 20000       | 1        | H1-H4 筛选                           |
| Step 3 结构决策 | 60               | 20000       | 1        | 章节结构设计                             |
| Step 4 内容生成 | 180              | 150000      | 1        | 上下文 40K+ tokens，`max_tokens=16000` |
| Step 5 自检   | 60               | 50000       | 1        | 独立 Evaluator                       |
| Step 6 输出   | —                | —           | 0        | 组装报告，无 LLM                         |
| **合计预算**    | **480**          | —           | **5**    | **与实测 \~8 分钟吻合**                   |

**关键发现**：

- 120 秒闸门不可达，因为单步预算加起来就是 480 秒
- Step 4 是主要瓶颈（180s 预算，曾卡死 5-10 分钟，见开发日志问题 4）
- `max_tokens=16000` 是 Step 4 慢的原因之一，开发日志记录降到 8000 后可加速到 2.5 分钟

**延迟优化路径**（阶段一收尾期执行，质量优先）：

1. 强制执行 `STEP_BUDGETS.timeout_seconds`（用 `asyncio.wait_for`）——✅ 已完成
2. 通过 `STEP4_MAX_TOKENS` 环境变量二分查找 Step 4 的安全冗余 max\_tokens 值（候选：16000→12000→10000→8000）——✅ 代码基础设施已完成，实测待用户跑真实 API
3. **质量是硬约束，延迟是软目标**：不通过降低质量标准来达成延迟目标。max\_tokens 压缩的目的是找到"不影响质量且有安全冗余的值"，不是一味压缩
4. 其他环节如存在必要的效率优化可继续寻找，但均不得牺牲质量和安全

**闸门调整**：阶段二进入闸门②从 ≤ 120 秒调整为"质量不下降前提下的实测值"。质量是硬约束，延迟是软目标——不通过降低质量标准来达成延迟目标。**300 秒不是硬性目标**，最重要的是保证输出质量。

## 七、各阶段接口兼容性保证（含行为语义差异声明）

### 7.1 `call_with_retry()` → `call_with_timeout()`（v3 改名）

```python
# v4 (打桩)
async def call_with_retry(fn, max_retries=2):
    for attempt in range(max_retries + 1):
        try:
            return await fn()
        except Exception:
            if attempt == max_retries: raise
            await asyncio.sleep(2 ** attempt)

# 阶段一收尾 P0-1 (改名 + 加超时) —— 签名兼容，增加可选参数
async def call_with_timeout(fn, max_retries=2, timeout_seconds=None):
    for attempt in range(max_retries + 1):
        try:
            if timeout_seconds:
                return await asyncio.wait_for(fn(), timeout=timeout_seconds)
            return await fn()
        except asyncio.TimeoutError:
            if attempt == max_retries: raise
            await asyncio.sleep(2 ** attempt)
        except Exception:
            if attempt == max_retries: raise
            await asyncio.sleep(2 ** attempt)
```

**v3 关键澄清**：

- **这不是 Circuit Breaker**。它没有 CLOSED/OPEN/HALF\_OPEN 状态机，没有熔断逻辑。
- 它只是给 `call_with_retry` 加了超时保护，防止 API 卡死时无限等待。
- 阶段三如需完整熔断，另建 `circuit_breaker_v2.py`，不在此函数上叠加。

**已知行为语义差异**：

- v4: 无超时保护，API 卡死时无限等待
- 阶段一收尾版: `timeout_seconds` 参数可选，默认不传保持 v4 行为兼容
- **调用方适配**：`asyncio.wait_for` 超时后抛出 `asyncio.TimeoutError`，调用方的外层 `try/except` 需能处理此异常（v4 的 `call_with_retry` 只抛业务异常）

### 7.2 `SimpleLogger` → `SessionEventLog`

```python
# v4 (打桩)
class SimpleLogger:
    def log(self, event_type: str, data: dict):
        print(f"[{event_type}] {data}")

# 阶段二 A 组 (完整实现) —— 签名兼容
class SessionEventLog:
    def log(self, event_type: str, data: dict):     # 签名相同
        ...
    def query(self, event_type=None, step_id=None):  # 新增
        ...
```

**已知行为语义差异**：

- v4: `log()` 同步执行；阶段二: JSONL 文件写入，需处理 `IOError`（**v3 新增：日志写入失败不应导致主流程崩溃，需 try/except 包裹并降级到 print**）
- v4: 输出到 stdout；阶段二: 输出到文件，stdout 需另外处理
- **v3 新增**：每个事件加 `trace_id` 字段，串联同一次运行的所有日志
- **v3.1.1 同步 v5.1**：① `trace_id` 改为注入式（`__init__` 接受 `trace_id` 参数，由 Orchestrator 统一生成并注入）；② 目录创建失败时降级到 print-only 模式（`log_path = None`，不崩溃）

### 7.3 `save_checkpoint` / `try_resume` → `CheckpointManager`

```python

def try_resume(industry_name: str) -> ReportState | None: ...
```

**已知行为语义差异**：

- v4: 单文件覆盖写入；阶段二: 多版本管理，每次 save 创建新版本文件
- v4: 无清理逻辑；阶段二: 自动过期清理（默认保留 7 天，**v3 新增：清理逻辑需有单元测试**）
- **v3 新增**：文件命名需考虑 `request_id` 扩展性（阶段三并发场景）
- **v3.1.1 同步 v5.1**：① 清理逻辑改用文件内 `saved_at` 字段（消除文件名字符串解析碰撞风险）；② `load_version` 的 `step_id` 必填（避免 glob 返回随机匹配）；③ `load()` 兼容 v4 遗留格式（纯 ReportState）和 v5 包装格式（`{"saved_at": ..., "state": ...}`）；④ 损坏文件分层清理（JSONDecodeError 直接删除，其他解析问题保留并记录）；⑤ `fromisoformat` 跨版本兼容（Python 3.9 不支持 `Z` 后缀，用 `.replace("Z", "+00:00")`）

## 十、附录：LangGraph 集成（可选技术探索）

（保持 v2/v2.5 原文不变）

LangGraph 的 StateGraph 在以下场景有价值：

- 步骤间出现**条件分支**（如"Step 3 决策后可能跳过 Step 4"）
- 需要**子图嵌套**（如 Step 1 内部有独立的搜索→压缩→总结 DAG）
- 需要**Human-in-the-Loop 断点重放**

**当前行业定义 Agent 的六步流程为严格线性**。用 LangGraph 替换当前的顺序 for 循环，不会带来功能增益——但会引入依赖、学习成本和调试复杂度。

**触发条件**（只有在以下需求确认时才考虑 LangGraph 集成）：

1. 方法论演进导致步骤间出现条件分支
2. 需要断点重放（非线性的 checkpoint 恢复，而非从头重跑）

**如果在阶段四引入 LangGraph**：预估工作量 5-7 天，但建议先在阶段三的 Harness Ablation 框架下做 A/B 对比（LangGraph Orchestrator vs 原生 Orchestrator），确认有实质性收益后再全量迁移。
