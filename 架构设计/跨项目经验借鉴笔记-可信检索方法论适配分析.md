# 跨项目经验借鉴笔记：可信检索方法论适配分析

> 日期：2026-08-13
> 来源文档：[行业定义Agent开发方法论-沉淀总结-2026-08-13.md](file:///Users/paper/trae_project/行业定义agent/行业定义Agent开发方法论-沉淀总结-2026-08-13.md)（trusted-retrieval-builder skill v2.1→v2.5.2 的 11 轮迭代沉淀）
> 本文档性质：思考笔记，记录"哪些经验值得借鉴、哪些需要适配、哪些不适用"的分析结论，供 B1-2 补搜优化和阶段三搜索源扩展时参考。
> 分析原则：不默认全盘接受，逐条验证技术前提与当前项目的匹配度。

## 一、来源项目与当前项目的关键差异

两项目虽都涉及"行业定义"，但搜索基础设施完全不同：

| 维度 | 来源项目（trusted-retrieval-builder） | 当前项目（demo2） |
|------|--------------------------------------|-----------------|
| 搜索方式 | 手动检索（WebFetch 逐页深评信源） | 自动搜索（Tavily API 返回片段） |
| 信源评估 | 三关深评（身份确认→数据溯源→数据状态） | 无逐页深评能力（片段不含页面元数据） |
| 信源管理 | 白名单 + 储备清单（跨会话持久化） | 无白名单（每次运行从头搜索） |
| 循环能力 | 双判断驱动停止（缺口闭合 + 期望收益枚举） | 固定轮次上限 2（预算驱动停止） |
| 报告类型 | 数据密集型（市场规模、面积、产量等可量化数字） | 定性分析型（行业边界、分类归属、技术路线） |
| 运行模式 | 多轮交互式（用户可授权追加轮次） | 一次性自动运行（用户输入行业名→系统产出报告） |

**核心约束**：来源项目的"双判断"和"白名单深评"依赖"能逐页打开信源核实"这个前提。当前项目用 Tavily API 返回搜索片段，无法做逐页深评。直接照搬会导致设计与基础设施不匹配。

## 二、值得借鉴的（3 条）

### 2.1 核心洞见："停止条件 = 证据决定，不是预算决定"

**来源**：沉淀总结 第三章 3.3

**原文要点**：v2.1-v2.4 用固定轮次上限，问题是"够用时就该停，不够用时轮次不够；搜满轮次才宣布找不到成为常见坏行为"。v2.5 演进为双判断——① 信息缺口闭合了吗？② 继续搜还有期望收益吗？预算降级为安全网而非驱动。

**与当前项目的对应**：当前 B1-2 方案是"把补搜上限从硬编码 2 改为环境变量可配置"——这只是把固定上限调大，没有改变"预算决定停止"的本质。5/5 行业补搜后仍有 1-4 个缺口，说明固定上限不够，但简单调大上限也不够。

**适配判断**：思路值得借鉴，但不能直接照搬。
- 判断①（缺口闭合）：当前已有，FM 审查检查信息缺口
- 判断②（期望收益）：当前没有，且无法完全实现——来源项目的"期望收益"依赖"未试动作枚举"（白名单剩余信源、未试关键词、储备候选），我们用 Tavily API 没有白名单体系
- **适配方案**：用"搜索结果质量"近似"期望收益"——如果连续补搜的搜索结果质量低（Tavily 返回结果少/不相关），即使没到上限也自动停止。做不了"还有哪些信源没试"的枚举，但可以判断"上一轮补搜是否带来了新信息"

### 2.2 "截断可见性"——记录未试动作和缺口原因

**来源**：沉淀总结 第三章 3.1 配套设计

**原文要点**：停止时交付"未试动作清单"，cap 截断不沉默。用户可授权追加轮次。

**与当前项目的适配**：用户明确指出——本项目是自动判断要做几轮的系统，不是让用户手动追加轮次。因此"截断可见性"的用途需要重新定义：
- **现阶段**：`data_gaps_remaining` 的 detail 是**开发迭代工具**——帮我们理解管线哪些环节搜不到、为什么搜不到，用于改进搜索策略
- **未来（阶段三）**：缺口记录是 Evaluator-Optimizer 闭环的**输入信号**——循环系统读缺口决定"要不要再搜一轮、换什么策略搜"。这正是路线图 v3.1 说的"阶段二预留接口让阶段三不需要返工数据结构"
- **用户侧语义**：报告里出现缺口标识 = "这个信息我们确认搜不到/当前能力做不到"，是诚实声明，不是求助

**适配方案**：增强 `data_gaps_remaining` 的 detail，记录"搜了什么 query + 搜到了什么 + 缺什么 + 为什么缺"，让未来循环系统有足够信息决定策略。不实现"用户手动追加轮次"功能。

### 2.3 "沉默即违规"

**来源**：沉淀总结 第二章 2.5

**原文要点**：每个槽位必须有终态：达标填上，或明确标空缺 + 原因。不许"没找到但没说"。

**与当前项目的对应**：当前 quality_flags 机制已部分实现——`data_gaps_remaining` flag 记录了缺口。但当前只记录了"有缺口"，**没有记录"每个缺口具体是什么 + 为什么搜不到"**（是 Tavily 没返回相关结果？还是结果质量不够？还是该信息确实不公开？）。

**适配方案**：在 `data_gaps_remaining` 的 detail 中拆分记录每个缺口的终态原因，让"沉默跳过"变成"显式声明搜不到"。

## 三、需要深度适配的（3 条）

### 3.1 两阶段分离（先建白名单再检索）

**来源**：沉淀总结 第二章 2.1

**原文要点**：Phase 1 不检索答案，只做信源发现 + 逐个深评 + 构建白名单；Phase 2 在白名单内检索。

**不适配原因（当前阶段）**：
- 前提是能逐页打开信源做"身份确认→数据溯源→数据状态"三关深评
- Tavily API 返回搜索片段，不含页面元数据，无法做三关深评
- 当前 6 步管线没有"Phase 1 信源发现"的步骤位置

**未来评估时机**：阶段三如果接入非碎片化搜索源（完整页面 web 搜索 / 内部知识库 / 专业数据接口），"逐页深评"的前提就满足了，两阶段分离可以重新评估。

**搜索源扩展方向（用户提出）**：
| 搜索类型 | 解决什么问题 | 适合阶段 |
|----------|------------|---------|
| 非碎片化 web 搜索（拿完整页面） | 当前 Tavily 返回片段太浅，无法深评 | 阶段三 |
| 内部知识库接口 | 行业定义内部积累的行业报告/数据库 | 阶段三/四 |
| 专业数据接口（行业数据库/统计局 API） | 口径纪律需要的权威一手数据 | 阶段三/四 |

**当前行动项**：确认 `search.py` 的接口设计是否已预留搜索源扩展性，让阶段三接入新搜索源时不需要改管线架构。

### 3.2 口径纪律

**来源**：沉淀总结 第四章 4.1-4.5

**原文要点**：口径层级匹配（防外部冒充）、连续性检查（防序列污染）、不等式禁令（防异口径推断）、等价判定默认拒绝（防自由心证放行）。

**适配判断**：面向数据密集型报告。当前项目生成的是定性分析报告（行业边界、分类归属、技术路线），定量数据较少。
- **4.1 口径层级匹配**：可迁移——即使定性报告也引用"某机构说 XX"，需防单一机构数字冒充全国
- **4.2-4.5 连续性检查/不等式禁令/等价判定**：当前不适用——报告以定性描述为主，无数字序列/不等式推断场景。等阶段三引入更复杂的数据分析时再评估

### 3.3 测试方法论

**来源**：沉淀总结 第七章 7.1-7.8

**原文要点**：判据写行为不写数字、执行者不知道判据、隔离清单、剧透效度声明、对照组防漂移、外部核销闭环、测试环境隔离。

**适配判断**：两个不同层次的测试。
- 来源项目测的是 **skill 的行为质量**（LLM 是否按规则行事）
- 当前项目测的是 **代码逻辑正确性**（pytest mock 测试）
- 不冲突，但不能直接迁移

**可借鉴**：7.1"判据写行为不写数字"——当前项目的测试已实践此原则（如 `test_search_phase_timeout_cascade` 验证行为"超时后是否 raise"，不是验证数字）。

## 四、对 B1-2 的修正方向

基于以上分析，B1-2 的设计目标从"调大补搜上限"修正为"让系统自动判断更聪明"：

1. **补搜停止逻辑升级**：从"固定上限 2"改为"双信号判断"——
   - 信号 A（缺口闭合）：当前已有，FM 审查检查信息缺口
   - 信号 B（期望收益止损）：连续补搜搜索结果质量低时自动停止（用搜索结果质量近似期望收益）
2. **环境变量上限保留为安全网**（兜底，非驱动）
3. **缺口记录增强**：记录"搜了什么 + 搜到了什么 + 缺什么 + 为什么缺"，为阶段三循环预留输入信号

**暂不实施**：等补搜问题深入讨论后再动手。当前先完成 B 组 P3 技术债务清理。
