
# 架构演进路线图 v2 — 行业定义 Agent 蓝图

> 版本：v2.0 | 日期：2026-06-05
> 定位：定义完整系统长什么样，以及从 Demo → 生产级的演进路径
> 起点：v4 Demo MVP（~760 行 Python）
> 终点：生产级系统（支持批量处理、多用户、成本可控、可审计）
>
> v2 基于 v1（蓝图初稿）的架构评审结果迭代。变更摘要：
> - 修正阶段二/三的工作量估计（v1 系统性偏低 30-50%）
> - 每个阶段增加"闸门条件"（什么情况下不进入下一阶段）
> - 接口兼容性增加"已知行为语义差异"声明
> - LangGraph 集成从阶段四必选项移至可选附录
> - 阶段三增加批处理排队策略

**核心设计原则（贯穿所有阶段）**：

1. **接口向前兼容**：v4 打桩的接口（`call_with_retry` → `CircuitBreaker.call`、`SimpleLogger` → `SessionEventLog`、`save_checkpoint` → `CheckpointManager`）在升级时只换实现不换签名
2. **质量组件不减**：Evaluator 独立化、Context Builder 四层、搜索并行压缩——这三个从 v4 起就完整实现，后续阶段只增强不替换
3. **基础设施逐步完善**：从 v4 的"print 日志"到生产的"审计管道"，从 v4 的"retry"到生产的"完整 Circuit Breaker"，逐步升级
4. **演进有闸门**：每个阶段有明确的进入条件和退出条件，什么情况下不升级和什么情况下升级同样重要

## 二、演进路径：四个阶段

### 阶段一：Demo MVP（v4，现在）

**目标**：跑一次出高质量报告，给人看不尴尬。

| 维度 | 状态 |
|---|---|
| **代码量** | ~760 行 Python |
| **运行方式** | `python frost_agent.py "行业名称"` |
| **Harness 组件** | 6 个完整做 + 5 个打桩 + 3 个不做 |
| **Environment** | Credential Vault (最小实现: .env) |
| **并发** | 无（单次 CLI 运行） |
| **持久化** | Checkpoint (save + load，极简) |
| **审计** | print 日志 |
| **成本** | 单一模型，~$0.03/次 [推测] |
| **延迟** | ~40-90 秒/次 [推测] |

**验收标准**：
- [ ] `python frost_agent.py "低空经济物流"` 稳定产出报告（3/3 次成功）
- [ ] Step 5 自检 C1-C5 逐项有 PASS/FAIL
- [ ] 报告不含竞争排名/市场规模/投资建议
- [ ] 自检 FAIL 时报告头部有警告标记
- [ ] 崩溃后可恢复（kill -9 后重跑）
- [ ] Step 1 搜索 < 10 秒
- [ ] 成本/延迟有实测数据（回填到 v4 文档第五章）

---

### 阶段二：内部试用（分析师使用）

**进入条件（闸门）**：以下全部满足方可进入阶段二，任意一条不满足则留在阶段一修复：

- [ ] 3 个不同行业的自检 C1-C5 全部 pass（或全部警告明确指向 LLM 能力边界）
- [ ] 单次运行端到端耗时 ≤ 120 秒
- [ ] 分析师试用的定性反馈 ≥ 3 条正向评价
- [ ] API 费用在可接受范围内（单次 < $0.10）

**退出条件**（什么情况下不进入阶段三）：如果阶段二运行 1 个月后：
- 分析师日均使用 < 3 次 → Demo 就够了，不需要 Web UI 和批量
- 方法论发生 > 3 次重大变更 → 先稳定方法论再升级基础设施

**新增需求**：
- 分析师一天可能跑 5-10 个行业，不能每次重新搜索
- 需要看到运行进度和 token 消耗
- 方法论可能需要调整（如新增规则 R6），不改代码就能生效
- 需要 Web UI（分析师不习惯命令行）

**升级项**：

| 组件 | v4 状态 | 阶段二升级 | 工作量（v2 修正） |
|---|---|---|---|
| **Persistent Memory** | 无 | SQLite 存储行业知识，相似行业复用历史经验 | 3-5 天 |
| **Session Event Log** | print | JSONL 结构化 + 查询接口（按 step/type 过滤） | 1 天 |
| **Token Audit** | StepOutput 字段 | 持久化审计日志 + 单次运行成本报表 | 0.5 天 |
| **Checkpoint** | save/load JSON | 多版本管理 + 过期清理 | 0.5 天 |
| **methodology/ 拆分** | 单文件 | 拆成 8 模块 + `_meta.yaml` + 版本校验 | 1 天 |
| **Circuit Breaker** | call_with_retry | 完整状态机（CLOSED/OPEN/HALF_OPEN）+ 按操作类型分组 | 1.5-2 天 |
| **Web UI** | 无 | Streamlit/Gradio：输入行业名 → 显示进度 → 展示报告 | 4-5 天 |
| **Sprint Contract** | prompt 内嵌 | 自动化协商（LLM 生成验收标准） | 2-3 天 |

**预计工作量**：~3-4 周（1 人）

> 注：v1 估计为 ~2 周。v2 修正基于以下考量：Persistent Memory 涉及知识表示 schema 设计、相似度匹配、缓存失效策略；Web UI 的"显示进度"需要 WebSocket/SSE 实时推送六步状态；Sprint Contract 自动协商涉及 prompt engineering 和验收标准可验证性验证。

### 阶段三：批量处理（生产化前奏）

**进入条件（闸门）**：
- [ ] 阶段二稳定运行至少 1 个月，无重大故障
- [ ] 累积 ≥ 50 个行业报告，方法论附注质量持续达标
- [ ] 需要批量处理的业务需求已确认（如"季度行业扫描需跑 50 个行业"）

**退出条件**：如果批量处理的月均请求 < 10 次，不升级到阶段四。API Server 即可满足需求，不需要完整的生产级基础设施。

**新增需求**：
- 批量输入（CSV/Excel 行业列表）
- 成本控制（不能 50 个行业烧掉几千美元）
- 结果批量导出
- API 接口供其他系统调用

**升级项**：

| 组件 | 阶段二状态 | 阶段三升级 | 工作量（v2 修正） |
|---|---|---|---|
| **Model Router** | 单一模型 | 按步骤选模型（搜索用 flash，生成用 sonnet）+ fallback 降级链 | 3-4 天 |
| **Prompt Cache** | 无 | 静态 System Prompt 前缀缓存对齐，降低 40-80% 成本 | 1 天 |
| **Rate Limiter** | 无 | API 调用频率限制，防止触发供应商限流 | 0.5 天 |
| **API Server** | 无 | FastAPI：POST /analyze（单个行业）+ POST /batch（批量） | 2-3 天 |
| **Evaluator-Optimizer 闭环** | 无（人工审查后修）| 最多 3 轮自动修正（保留人工 override） | 2 天 |
| **Output Safety** | 最小实现 | 完整 workspace 边界检查 + 版本命名（自动追加时间戳） | 0.5 天 |
| **Harness Ablation** | 无 | 可开关单个 harness 组件，对比质量/成本 | 1 天 |
| **批处理排队策略** | 无 | FIFO 队列 + 最大并发数限制（≤ 3 个行业同时运行） | 1.5-2 天 |

**预计工作量**：~3-4 周（1 人）

> 注：v1 估计为 ~2-3 周。v2 修正基于：Model Router 涉及多模型配置管理、降级链每种失败模式测试、API 密钥隔离；批处理排队策略是与单次运行的实质性架构变更。

### 阶段四：生产级（行业定义内部工具）

**进入条件（闸门）**：
- [ ] 阶段三稳定运行至少 3 个月
- [ ] 月均处理 ≥ 100 个行业
- [ ] 多用户并发需求已确认（≥ 3 个分析师同时使用）
- [ ] 审计合规需求已确认（如客户要求追踪每个报告的生成过程）

**退出条件**：如果阶段三已满足所有业务需求（批量处理 + API 接口），阶段四可部分跳过。不是每个组件都必须升级到阶段四——按实际需求选择性升级。

**新增需求**：
- 多用户并发（多个分析师同时使用）
- 完整审计链（谁、什么时候、分析了什么行业、消耗多少 token）
- 成本预算和告警
- 方法论版本管理（灰度发布新方法论）
- 可选：Human-in-the-Loop（高风险行业人工确认）

**升级项**：

| 组件 | 阶段三状态 | 阶段四升级 | 工作量 |
|---|---|---|---|
| **Session Event Log** | JSONL | 接入审计管道（如 ELK/ClickHouse），支持跨会话查询 | 3-5 天 |
| **Credential Vault** | .env | 加密存储（如 HashiCorp Vault），支持多环境（dev/staging/prod） | 2-3 天 |
| **Human-in-the-Loop** | 无 | Step 5 自检失败后暂停，等待人工确认再继续 | 2-3 天 |
| **方法论文档版本管理** | 拆分 + 版本校验 | 灰度发布（部分用户用 v2.1，部分用 v2.2） | 3-5 天 |
| **Persistent Memory** | SQLite | 接入向量数据库（如 Chroma），支持语义相似行业搜索 | 3-5 天 |
| **Docker Sandbox** | 无 | 可选：若未来引入代码执行能力，用 Docker 隔离 | 3-5 天 |

**预计工作量**：~1 个月（1-2 人）

## 三、各阶段接口兼容性保证（含行为语义差异声明）

### 3.1 `call_with_retry()` → `CircuitBreaker.call()`

```python
# v4 (打桩)
async def call_with_retry(fn, max_retries=2):
    for attempt in range(max_retries + 1):
        try:
            return await fn()
        except Exception:
            if attempt == max_retries: raise
            await asyncio.sleep(2 ** attempt)

# 阶段二 (完整实现) —— 签名兼容
class CircuitBreaker:
    async def call(self, fn, *args, **kwargs):
        # 完整状态机实现
        ...
```

**已知行为语义差异**：
- v4: `call_with_retry` 是模块级函数，无状态；阶段二: `CircuitBreaker.call` 是实例方法，需在 Orchestrator 中持有 `CircuitBreaker` 实例
- v4: 重试不计入断路状态；阶段二: 连续 `max_failures` 次失败后断路拒绝所有请求 30 秒
- **调用方适配**：Orchestrator 初始化时创建 `self.breaker = CircuitBreaker(max_failures=3)`，替换 `await call_with_retry(fn)` 为 `await self.breaker.call(fn)`

### 3.2 `SimpleLogger` → `SessionEventLog`

```python
# v4 (打桩)
class SimpleLogger:
    def log(self, event_type: str, data: dict):
        print(f"[{event_type}] {data}")

# 阶段二 (完整实现) —— 签名兼容
class SessionEventLog:
    def log(self, event_type: str, data: dict):     # 签名相同
        ...
    def query(self, event_type=None, step_id=None):  # 新增
        ...
```

**已知行为语义差异**：
- v4: `log()` 同步执行；阶段二: JSONL 文件写入，需处理 `IOError`
- v4: 输出到 stdout；阶段二: 输出到文件，stdout 需另外处理
- **调用方适配**：阶段二的 `SessionEventLog.log()` 需要 try/except 包裹文件写入失败，v4 不需要

### 3.3 `save_checkpoint` / `try_resume` → `CheckpointManager`

```python
# v4 (打桩)
def save_checkpoint(state: ReportState, step_id: str): ...
def try_resume(industry_name: str) -> ReportState | None: ...

# 阶段二 (完整实现)
class CheckpointManager:
    def save(self, state: ReportState, step_id: str): ...
    def load(self, industry_name: str) -> ReportState | None: ...
```

**已知行为语义差异**：
- v4: 单文件覆盖写入；阶段二: 多版本管理，每次 save 创建新版本文件
- v4: 无清理逻辑；阶段二: 自动过期清理（默认保留 7 天）
- v4: `step_id` 参数用于命名（如 `{industry}_{step_id}.json`）；阶段二: `step_id` 用于版本标记
- **调用方适配**：v4 的调用 `save_checkpoint(state, step_id)` 可无缝替换为 `checkpoint_mgr.save(state, step_id)`。阶段二首次运行时磁盘占用会增长（多版本），需在文档中说明。

### 3.4 Sprint Contract (prompt 内嵌) → `SprintContract` 对象

- v4: 验收标准写进 `STEP_TASKS` 字典的 task prompt 文本中
- 阶段二: `SprintContract` 对象化，`negotiate()` 用 LLM 自动生成验收标准
- **兼容性**：阶段二可以在 Orchestrator 中新增可选逻辑（检查 `SprintContract` 是否存在），不影响 v4 的 prompt 内嵌方式。原有 `STEP_TASKS` 保持不动。

### 3.5 Token Audit (StepOutput 字段) → `TokenAudit`

- v4: `StepOutput.token_usage` 字典字段
- 阶段二: `TokenAudit` 类读取 `StepOutput.token_usage` 生成持久化报表
- **兼容性**：完全不破坏现有代码。`TokenAudit.record()` 从已有 `StepOutput` 读取数据，不改变 `StepOutput` 模型。

## 四、关键决策记录

| 决策 | v4 选择 | 未来可能变更 |
|---|---|---|
| **单 Agent vs 多 Agent** | 单 Agent | 阶段四可评估 Planner+Generator+Evaluator 三 Agent（仅当出现非线性编排需求时） |
| **状态管理** | ReportState 内存对象 | 阶段三可评估 LangGraph StateGraph（仅当出现条件分支/子图需求时） |
| **搜索工具** | Tavily API | 阶段三可接入多个搜索源（Tavily + Serper + 自建） |
| **模型** | 单一模型 | 阶段二开始 Model Router，阶段三多模型降级 |
| **方法论存储** | 单文件 markdown | 阶段二拆分为模块 + `_meta.yaml` |
| **持久化** | Checkpoint JSON | 阶段二 SQLite，阶段四向量数据库 |
| **审计** | print | 阶段二 JSONL，阶段四审计管道 |

## 五、风险与应对

| 风险 | 阶段 | 应对措施 |
|---|---|---|
| Demo 不稳定（API 超时/限流） | v4 | `call_with_retry` + 搜索全失败降级 |
| 方法论理解偏差（LLM 没按规则执行） | v4 | Independent Evaluator 拦截 + Step 5 失败警告注入 |
| 成本超预算（阶段三批量处理） | 阶段三 | Model Router + Token Audit + 批处理 FIFO 队列限制并发 |
| 方法论频繁变更 | 阶段二 | 外部加载 + 版本校验，不改代码 |
| 多用户并发冲突 | 阶段四 | Checkpoint 按用户隔离 + SQLite 事务 |
| 阶段二升级后被基础设施复杂度拖累 | 阶段二→三 | 闸门条件阻止过早升级；如果 Demo 已满足分析师需求则不升级 |

## 六、附录：LangGraph 集成（可选技术探索）

LangGraph 的 StateGraph 在以下场景有价值：
- 步骤间出现**条件分支**（如"Step 3 决策后可能跳过 Step 4"）
- 需要**子图嵌套**（如 Step 1 内部有独立的搜索→压缩→总结 DAG）
- 需要**Human-in-the-Loop 断点重放**

**当前行业定义 Agent 的六步流程为严格线性**（Step 1→2→3→4→5→6，永远按固定顺序执行）。用 LangGraph 替换当前的顺序 for 循环，不会带来功能增益——但会引入依赖、学习成本和调试复杂度。

**触发条件**（只有在以下需求确认时才考虑 LangGraph 集成）：
1. 方法论演进导致步骤间出现条件分支
2. 需要断点重放（非线性的 checkpoint 恢复，而非从头重跑）

**如果在阶段四引入 LangGraph**：预估工作量 5-7 天，但建议先在阶段三的 Harness Ablation 框架下做 A/B 对比（LangGraph Orchestrator vs 原生 Orchestrator），确认有实质性收益后再全量迁移。
