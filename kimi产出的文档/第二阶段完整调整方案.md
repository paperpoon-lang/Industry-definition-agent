# 行业定义 Agent — 第二阶段完整调整方案

> **面向**：项目负责人 + Trae（开发助手）  
> **目的**：基于阶段一多行业验证结果，重新确定阶段二的完整范围、优先级、接口预留  
> **前提**：阶段一已验证通过多个行业（低空经济物流、汽车、新能源汽车），报告质量稳定，管线基本可靠  
> **评估立场**：协作式建议，非权威指令  
> **日期**：2026-06-12

## 一、为什么需要重新调整阶段二

路线图 v2（2026-06-05 编写）是在阶段一尚未完成时制定的**前瞻性假设**。现在阶段一已跑通多个行业，有了真实的验证数据，阶段二的范围不应该照搬路线图，而应该**基于实际痛点重新裁剪**。

**核心判断：路线图 v2 的阶段二有"假设性需求驱动"的风险。**

路线图 v2 列出的 4 个"新增需求"（分析师一天跑 5-10 个行业、需要看到进度和 token 消耗、方法论需要调整、需要 Web UI）**都是未经证实的假设**。阶段二不应该为假设埋单。

## 二、阶段二 A 组（必须做，1-1.5 周）

这些是**已验证的痛点**或**成本极低的基础设施**。必须做，不取决于使用模式。

| 组件 | 工作量 | 为什么必须做 | 关键设计约束 |
|------|--------|------------|-------------|
| **`quality_flags` 机制** | 0.5 天 | 阶段一真实发现的静默降级风险。`or` fallback 防止了崩溃，但让降级信息"消失在状态对象的一个字段里" | 写入 `StepOutput` 独立字段（不污染 `result`），Step 6 汇总到报告尾部，同时为阶段三循环预留**机器可读的信号** |
| **Session Event Log → JSONL** | 1 天 | 从 print 升级到 JSONL，为后续调试和审计打基础。即使只有一个分析师，开发者也需要结构化日志 | 按 step/type 过滤，append-only 写入，支持查询接口 |
| **Token Audit → 持久化** | 0.5 天 | 让成本从推测变实测。阶段二闸门条件"费用 <$0.10"需要它 | 读取 `StepOutput.token_usage`，生成单次运行成本报表 |
| **Checkpoint → 多版本 + 过期清理** | 0.5 天 | 当前覆盖写入已够用，但多版本是更安全的默认。同时为阶段三循环预留**可恢复的旧版本** | 每次 save 创建新版本，自动保留 7 天 |
| **Output Safety（输出安全）** | 0.5 天 | 当前阶段一的报告保存是**覆盖写入**。如果分析师跑了两次同一个行业，第二次完全覆盖第一次。这是**真实风险，不是假设** | 文件名自动追加时间戳或版本号（如 `新能源汽车_20250612_143052_行业定义报告.md`），检测到已存在时追加 `_v2` |
| **methodology/ → 简化拆分** | 0.5-1 天 | 当前痛点是"方法论调整需要改代码"，不是"单文件太大"。**简化**：不是"拆成 8 模块"，而是拆成 2-3 模块 + `_meta.yaml` 版本声明 | 保持正则切片逻辑，只把最可能独立变更的章节（如 Hard Rules、Heuristics、自检清单）拆出，主文件保留框架 |

**A 组总计：约 3.5-5 天，加上调试和文档，1-1.5 周。**

**A 组的核心原则：阶段二只做"已验证的痛点" + "成本极低的基础设施" + "阶段三循环的接口预留"。**

## 三、阶段二 B 组（有条件做，取决于开发者自测，1-2 周）

这些是**假设性需求**，需要在"开发者自测验证"后决定是否做。如果自测结果不支持，全部跳过。

| 组件 | 工作量 | 触发条件 | 验证方式 |
|------|--------|---------|---------|
| **Persistent Memory (SQLite)** | 3-5 天 | 如果实际使用频率 **≥ 每天 3 个行业**，或方法论规则冲突的压力测试需要跨行业对比 | 开发者自测记录：频率 |
| **Circuit Breaker（极简版）** | 0.5 天 | 如果 API 超时/卡死问题出现（如 Step 4 卡死 5-10 分钟） | 开发者自测记录：API 超时情况 |

**B 组总计：如果两项都做，约 1-2 周；如果都不做，0 周。**

**关于 Circuit Breaker 的简化：** 不做完整三态状态机（CLOSED/OPEN/HALF_OPEN），先用 `asyncio.wait_for` 在 `call_with_retry` 层面加超时保护。这是最低成本解决最痛"无限等待"问题的方式。如果后续 API 稳定性问题持续出现，再在阶段三升级为完整状态机。

## 四、阶段二 C 组（可选做，取决于开发者自测，2 周）

这些是**体验升级**，不是功能必需。如果开发者自测或实际使用者明确需要，才做；如果不需要，全部跳过。

| 组件 | 工作量 | 触发条件 | 验证方式 |
|------|--------|---------|---------|
| **Web UI (Streamlit/Gradio)** | 4-5 天 | 如果开发者自测或实际使用者明确反馈**"命令行不方便"**或**"需要给非技术用户展示"** | 开发者自测记录：体验 |
| **Sprint Contract (自动化协商)** | 2-3 天 | 如果 `STEP_TASKS` 的验收标准**需要频繁调整**（目前运行稳定，需求不迫切） | 开发者自测记录：是否需要调整方法论规则 |

**C 组总计：如果两项都做，约 2 周；如果都不做，0 周。**

**C 组的核心原则：Web UI 是阶段二最大的单块（4-5 天）。如果分析师实际对命令行无意见，这笔投入完全浪费。**

## 五、阶段二 D 组（明确推迟到阶段三）

| 组件 | 路线图 v2 原安排 | 推迟原因 |
|------|-----------------|---------|
| **Model Router** | 阶段三 | 当前单一模型运行稳定，无降级需求 |
| **Prompt Cache** | 阶段三 | 当前成本在可接受范围内，不需要优化 |
| **API Server** | 阶段三 | 没有批量处理需求确认 |
| **Rate Limiter** | 阶段三 | 没有 API 限流问题 |

**D 组的核心原则：阶段二不为未来需求做过多准备。阶段三的需求在阶段二运行 1 个月后会自然浮现。**

## 六、关键新增：阶段三循环的接口预留

路线图 v2 把循环（Evaluator-Optimizer 闭环）放在**阶段三**。这个判断合理——阶段二需要先有稳定的 Evaluator 基线，循环才有可靠的停止条件。

**但阶段二必须做循环的"接口预留"：**

| 阶段二预留 | 为什么阶段三需要它 | 如果不预留的后果 |
|-----------|------------------|---------------|
| **`quality_flags` 标准化格式** | 循环需要知道"失败的是哪一步"，决定重跑哪一步 | 阶段三做循环时，需要重新解析 `reasoning` 文本，不可靠 |
| **Checkpoint 多版本** | 循环需要恢复到某一步的旧版本，重跑后续步骤 | 阶段三覆盖写入的 checkpoint 无法恢复旧版本，循环只能从头重跑 |
| **Step 5 `fixes_required` 结构化** | 循环需要读取"修复建议"，生成重跑策略 | 阶段二如果是文本列表，阶段三需要重新解析 |

**预留的具体实现：**

```python
# models.py — StepOutput 中 quality_flags 的标准化格式
class StepOutput(BaseModel):
    # ... 现有字段 ...
    quality_flags: list[str] = Field(default_factory=list)
    # 格式约定："{category}:{field}:{severity}"
    # 示例："llm_empty_field:summary:high", "search_partial_failure:2/3:medium"

# Step 5 fixes_required 的结构化
class FixItem(BaseModel):
    dimension: str           # 如 "C4", "llm_empty_field"
    problem: str             # 问题描述
    target_step: str | None  # 建议重跑的步骤（如 "1_info_collection"），None 表示不指定
    severity: str            # "high" / "medium" / "low"

# 这样阶段三的循环逻辑可以直接：
# for fix in eval_result.fixes_required:
#     if fix.target_step and fix.severity == "high":
#         return fix.target_step  # 精确重跑 Step 1
```
**这不是"提前做循环"，而是"阶段二设计时，让阶段三不需要返工阶段二的数据结构"。**

**关于 `FixItem` 结构化：** 当前阶段二不做 `FixItem` 的 Pydantic 模型实现。`evaluator.py` 的 `fixes_required` 保持为 `list[str]`（简单字符串列表）。`FixItem` 的设计保留为注释/文档中的设计笔记，供阶段三参考。阶段二只需要 `quality_flags` 的标准化字符串格式即可。

## 七、进入阶段二前的关键步骤：开发者自测验证（0.5-1 天）

路线图 v2 把"分析师试用反馈 ≥ 3 条正向"作为进入条件，但当前项目还没有分析师用户在使用它。建议在正式进入阶段二编码前，花 0.5-1 天时间做"开发者自测验证"——用已有的 checkpoint 数据回溯分析，记录自己运行时的痛点。

### 7.1 开发者自测记录表

开发者在 1 天内跑 3-5 个行业，记录以下数据：

| 记录项 | 记录方式 | 用途 |
|--------|---------|------|
| 每次运行实际耗时 | 秒表计时或日志时间戳 | 验证是否 ≤ 120 秒（阶段二闸门条件） |
| 每次运行实际 token 消耗 | 从报告尾部读取 | 验证是否 <$0.10（阶段二闸门条件） |
| 是否遇到方法论调整场景 | 记录行业名和具体问题 | 判断 methodology 拆分是否紧迫 |
| 是否对命令行有具体怨言 | 记录具体环节 | 判断 Web UI 是否需要 |
| 同一行业重复运行时的覆盖问题 | 检查 reports/ 目录 | 验证 Output Safety 的必要性 |
| API 超时/卡死情况 | 记录发生步骤和时长 | 判断 Circuit Breaker 极简版是否需要 |

### 7.2 基于自测数据决定阶段二范围

| 如果自测数据显示... | 阶段二范围应该是... |
|---------------------|-------------------|
| 每天跑 3+ 个行业，命令行够用 | **A 组 + B 组（Persistent Memory）** ≈ 2-3 周 |
| 每天跑 3+ 个行业，命令行不够 | **A 组 + B 组 + C 组（Web UI）** ≈ 3-4 周 |
| 每周跑 1-2 个行业，命令行够用 | **只做 A 组** ≈ 1-1.5 周 |
| 每周跑 1-2 个行业，但需要给老板展示 | **A 组 + C 组（Web UI）** ≈ 2-3 周 |
| 出现 Step 4 卡死 5-10 分钟 | **A 组 + B 组（Circuit Breaker 极简版）** ≈ 1.5-2 周 |

**B/C 组触发条件改为"当实际使用频率达到阈值时再触发"**，而不是现在就去假设需求。

## 九、风险与应对

| 风险 | 阶段 | 应对措施 |
|------|------|---------|
| 阶段二范围膨胀（做了假设需求） | 阶段二 | 严格执行 A/B/C/D 分组，B/C 组必须依赖开发者自测数据 |

| 方法论频繁变更，阶段二 methodology 拆分后又要改 | 阶段二 | 简化拆分（2-3 模块而非 8 模块），只拆最可能独立变更的章节 |

## 十、总结：我的倾向性建议

**阶段二不应该做路线图 v2 列出的全部 8 个组件。**

**阶段二应该做：**

1. **A 组（1-1.5 周）**：`quality_flags` + Session Event Log + Token Audit + Checkpoint + Output Safety + methodology 简化拆分。这是已验证的痛点 + 成本极低的基础设施 + 阶段三循环的接口预留。

2. **开发者自测验证（0.5-1 天）**：跑 3-5 个行业，记录频率、耗时、痛点、成本、API 超时情况。

3. **基于验证结果决定 B/C 组**：
   - 高频使用 + 需要图形界面 → A + B + C ≈ 3-4 周
   - 高频使用 + 命令行够用 → A + B ≈ 2-3 周
   - 低频使用 → **只做 A 组，1-1.5 周结束阶段二**
   - 出现 Step 4 卡死 → A + B（Circuit Breaker 极简版）≈ 1.5-2 周

**核心原则：**
- **不为假设埋单**（B/C 组取决于验证）
- **不为升级而升级**（Circuit Breaker、Web UI 如果不需要就不做）
- **为阶段三循环预留接口**（`quality_flags`、Checkpoint 多版本、结构化 `fixes_required`）
- **Output Safety 是真实风险，不是假设，从阶段三提上来**
