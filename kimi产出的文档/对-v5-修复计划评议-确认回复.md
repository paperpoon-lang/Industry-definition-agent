## 一、确认：5 个反驳全部有理，我修正 3 个判断，接受 2 个不采纳建议

### 1. 反驳 1：Q1 验收标准"接受偶发超时"——**我的判断有误，接受反驳**

你的反驳完全正确。我确实混淆了两类超时：

- **环境故障超时**（API 余额不足、网络中断）：偶发，不在修复范围内，出现时不算修复失败
- **API 响应慢超时**（60s 内未返回）：恰恰是修复 P2 #4 要解决的核心问题，修复后必须消除

我的建议"0/5 通过但记录偶发超时为已知限制"模糊了这两者的区别。这会导致验收时看到超时就"接受"，而不是追问"这是 API 响应慢还是环境故障"。

**修正后的判断**：
- 验收标准：**0 超时**
- 但出现超时时必须分析根因：
  - 环境故障（余额/网络）→ 记录为环境限制，不算修复失败
  - API 响应慢（60s 不够）→ 修复不充分，需调高 timeout
- 这与我提示词中"验证断言而非信任断言"的原则一致——不因为"偶发"就接受，而是追问根因

### 2. 反驳 2：Q4 STEP_BUDGETS 增到 360s——**我的判断有误，接受反驳**

你的反驳完全正确。我犯了架构层面的错误：

- `STEP_BUDGETS["1_info_collection"].timeout_seconds=180` 作用于 `call_with_timeout(fn, timeout_seconds=180)`，即**单次 LLM 调用**的超时
- 不是"步骤整体预算"，而是"LLM 调用卡死时的兜底"
- 增到 360s 会让 LLM 调用在 API 卡死时等 **360s × 3 次（含重试）= 18 分钟** 才报错，反而降低可靠性
- 分层设计（搜索阶段 300s 外层 `asyncio.wait_for` + LLM 调用 180s 内层 `call_with_timeout`）是正确的——两个独立的超时控制两个独立的子系统

**修正后的判断**：
- `STEP_BUDGETS` 的 Step 1 timeout 保持 **180s**
- 搜索阶段的外层 300s timeout 是独立机制，不替代 `STEP_BUDGETS`
- 只需在文档中明确说明两个 timeout 的分层职责

### 3. 反驳 3：Step 3 与 Step 1 的因果链假设——**我的判断有误，接受反驳**

你的反驳完全正确。我假设了一个没有证据的因果链：

> 钙钛矿 FM 审查超时 → 补搜未执行 → 信息不足 → Step 3 prompt 更复杂 → Step 3 超时

这个逻辑链有 3 个漏洞：

1. **根因已确认**：开发日志明确说钙钛矿 Step 3 超时是"硅基流动 API 响应慢"，不是 prompt 复杂度问题
2. **逻辑不通**：如果信息不足导致 Step 3 问题，应该表现为**返回质量差**（维度选错、结构不合理），而不是**超时**。超时是时间维度的问题，与信息充分性（质量维度）无直接关联
3. **反例成立**：其他 4 个行业信息更充分（补搜执行了），但 Step 3 的 LLM 调用任务相同，不会因为"信息更充分"就显著更快

**修正后的判断**：
- 删除评议报告中的 P3 风险"Step 3 超时与 Step 1 搜索质量的关联"
- 钙钛矿 Step 3 超时是独立问题（API 响应慢），与 Step 1 无关
- 观察钙钛矿在修复后 Step 3 是否仍超时是有价值的验证数据，但**不应该假设因果链存在**

### 4. 反驳 4：`_error_type` 改名——**我的风险高估，接受反驳**

你的反驳合理。`_error_type` 是 `_fm_review_search_results` 函数内部返回的 Python dict 字段，不是 LLM 返回的 JSON 字段：

- 正常路径：LLM 返回 → `_parse_json_response` → 提取 `data_gaps`/`suggested_queries` → 返回正常 dict
- 异常路径：直接返回 `{"_error_type": "timeout"}`，不经过 LLM
- 调用方先检查 `"_error_type" in fm_result`，如果是正常 dict 就不会进入错误分支
- LLM 生成以下划线开头的 JSON 字段概率极低，且即使生成了，正常路径的 dict 不会包含 `_error_type`（因为正常路径只返回 `data_gaps` 和 `suggested_queries`）

**判断**：改名成本极低，但收益也极低。属于"过度防御"。**不采纳改名建议**，但保留为 P3 可选项（如果未来出现实际冲突再改）。

### 5. 反驳 5：修改点"8 处"的计数——**部分有理，但不影响结论**

你的反驳合理。我按"函数签名修改、调用点修改"等维度拆分，确实有"文字游戏"成分：

- 如果按我的逻辑，`_fm_review_search_results` 重写内部也有多处修改（try/except/return/logger），是不是也该拆？
- 实际上，6 处和 8 处都是同一个函数链的修改，实际工作量差别不大
- 4-6h vs 5-7h 的差别在工程估算中属于正常误差范围

**判断**：工作量上调到 5-7h 偏保守，但不算错。评议报告的总工作量 10-15h 可以保留，也可以回到 8-13h（差异不大）。**不影响执行决策**。

## 三、对 4 个核心问题的确认

### Q1：测试是否作为 A 组交付物？

**你的回答：是。我确认。**

理由完全同意：修复 1 改了 `_fm_review_search_results` 的返回契约（`{}` → `{"_error_type": ...}`），这是核心逻辑变更。没有持久化测试，下次改代码时无法快速验证是否破坏修复 1。`agent-code-validator` 的临时验证不可重复执行。3-4h 的测试投入值得。

**补充**：测试依赖 `pytest>=7.0` 和 `pytest-asyncio>=0.21.0` 需要补充到 `requirements.txt` 或 `tests/requirements.txt`。测试耗时优化（`sleep(70)` → mock `call_with_timeout` 直接抛异常）需要一并实现，否则单个测试 121s 不可接受。

### Q2：验收标准是否接受方案 B？

**你的回答：不接受"接受偶发"的部分，但接受"分析原因后再判定"的思路。我确认。**

正确的验收标准：
- **目标：0 超时**
- 出现超时后的分析流程：
  1. 检查是否是环境故障（余额不足、网络中断）→ 记录为环境限制，**不算修复失败**
  2. 检查是否是 API 响应慢（60s 内未返回）→ **修复不充分**，需调高 `FM_REVIEW_TIMEOUT`
- 不应该无原则地"接受偶发"

这与我的提示词中"验证断言而非信任断言"的原则一致。我之前犯了"因为偶发就降低标准"的错误。

### Q3：`STEP_BUDGETS` 的 Step 1 timeout 是否调整？

**你的回答：不调整，保持 180s。我确认。**

理由完全同意：

### Q4：FM 审查日志的 `step_id` 是否增加轮次区分？

**你的回答：是，通过 `data.round_label` 字段，不改 `step_id` 本身。我确认。**
