核心设计原则
跑一次就出高质量报告
Demo 不是 7×24 生产系统。对报告质量有直接影响的组件完整实现，基础设施保留接口、实现从简。
严格线性，不做 E-O 闭环
Step 5 自检失败时只注入警告标记，不自动重跑 Step 4。遵守项目 Brief 约束 #3："不通过则标记，不允许直接输出"。
独立 Evaluator 防自评偏差
Evaluator 只看最终报告文本，不接收生成过程的 reasoning。把"干活"和"挑刺"彻底分开，解决 Self-Evaluation Bias。
v4 关键改进（相比 v3）： Context Builder 三层 → 四层（新增任务指令层）｜ Step 5 失败处置：增加警告注入逻辑 ｜ methodology_loader：修正 SLICE_MAP 关键词，增加空切片降级 ｜ 新增成本/延迟估算章节

STEP 01 信息收集 — 并行搜索 + LLM 总结
输入
  • 行业名称（CLI 参数）
  • Context Builder 四层上下文
  • Tavily API Key（环境变量）
处理逻辑
  • 3 个 query 并行搜索（asyncio.gather）
  • 单条结果 >1500 字符截断
  • 全失败时降级为单 query 重试
  • LLM 总结为结构化 JSON
输出格式（JSON）
  • summary — 行业概述
  • official_definitions — 官方定义
  • key_regulations — 关键政策
  • structural_factors — 结构性因素
  • adjacent_industries — 相邻行业
  • data_gaps — 数据缺口
方法论引用
  • §3.2 信息优先级(P0-P3)
  • §6 参考框架(GICS/NAICS)
  • Hard Rules R1-R5
# 搜索查询模板（3 个维度并行） SEARCH_QUERIES = [ "{industry} 行业定义 官方定义 标准", "{industry} 政策 监管 产业链", "{industry} 边界 与相邻行业区分", ]
STEP 02 维度筛选 — H1-H4 原则应用
输入
  • Step 1 的信息收集结果
  • Context Builder 四层上下文
  • 方法论 §3.1 维度筛选原则
处理逻辑
  • 应用 H1：独特形态 / 被极端放大
  • 应用 H2：独立侧（≥2 个）
  • 应用 H3：经营结果传导
  • 应用 H4：数据可获得性
  • 明确记录：选了什么、放弃了什么、为什么
输出格式（JSON）
  • selected_dimensions — 选中维度列表
  • abandoned_dimensions — 放弃维度及原因
  • reasoning — 筛选推理过程
验收标准
  • 覆盖 ≥ 2 个独立侧
  • 每个维度有经营结果传导
  • 放弃维度必须记录原因
# H1-H4 维度筛选原则 H1: 独特形态 / 被极端放大 → 决定行业"长什么样" H2: 独立侧 ≥2 个 → 技术/制度/需求/成本 H3: 经营结果传导 → 每个维度影响商业决策 H4: 数据可获得性 → 合法筛选标准
STEP 03 结构决策 — 报告章节设计
输入
  • Step 2 的维度筛选结果
  • Context Builder 四层上下文
  • 方法论 §3.4 报告结构启发式
处理逻辑
  • 每章对应 Step 2 至少一个维度
  • 严格禁止竞争格局/市场规模/投资建议章节
  • 方法论附注章解释维度取舍
输出格式（JSON）
  • chapters — 章节列表（title, dimensions, summary）
  • reasoning — 结构设计推理
典型结构
  • 一、行业核心定义
  • 二、行业边界划定
  • 三、结构性特征分析
  • 四、制度与监管环境
  • 五、方法论附注
STEP 04 内容生成 — 撰写完整报告
输入
  • Step 3 的章节结构
  • Step 1 的信息收集结果
  • Context Builder 四层上下文
  • 方法论 Hard Rules + 推理展示要求
处理逻辑
  • 直接输出 Markdown（从 # 标题开始）
  • 剥离开场白（_strip_preamble）
  • 每个关键判断附带推理链和置信度
  • 所有数据标注来源和可信度
严格禁止内容
  • ❌ 企业排名 / 市场份额
  • ❌ 竞争格局分析
  • ❌ 市场规模预测
  • ❌ 投资建议
输出格式
  • Markdown 完整报告
  • 存储于 step.result.report_text
  • 最长步骤（15-35 秒）
瓶颈步骤：Step 4 是端到端最大瓶颈，长报告可能需要 90 秒。建议演示时预先运行保存结果。
STEP 05 自检 — Independent Evaluator
输入
  • Step 4 生成的报告文本（仅最终文本）
  • 行业名称
  • 不接收 Step 1-4 的 reasoning
处理逻辑
  • 独立 LLM 调用（不同 prompt）
  • C1-C5 逐项审查
  • 每个维度 PASS/FAIL + 具体问题
  • 总体：pass / fail_with_fixes
输出格式（JSON）
  • overall — pass / fail_with_fixes
  • evaluator_confidence — high/medium/low
  • dimensions.C1-C5 — status + detail
  • failed_dimensions — 未通过列表
  • issues — 具体问题
  • fixes_required — 修复建议
v4 关键约束
  • 失败时只注入警告
  • 不自动重跑 Step 4
  • 遵守 Brief 约束 #3
设计意图：把"干活"和"挑刺"彻底分开。Evaluator 是独立的审查员，倾向于发现问题而非确认一切正常。这是解决 Self-Evaluation Bias 的核心机制。
STEP 06 输出 — 组装最终报告
输入
  • Step 4 报告正文
  • Step 5 自检结果（若失败）
  • 各步骤 token_usage 统计
处理逻辑
  • 自检通过 → 直接输出报告
  • 自检失败 → 头部注入 ⚠️ 警告
  • 尾部附加 Token 统计
  • 写入 reports/{行业}_行业定义报告.md
警告格式（失败时）
  • ## ⚠️ 自检未通过
  • 列出失败维度
  • 列出具体问题
  • 请人工审查后再使用此报告
输出文件
  • Markdown 报告文件
  • Checkpoint JSON（状态持久化）
  • Console 预览（前 500 字符）

Context Builder — 四层上下文组装器
v4 核心改进：新增"任务指令层"（Layer 3），将每步的任务描述和 Sprint Contract 验收标准直接注入上下文。
LAYER 1
静态身份
_static_identity() — 固定不变的系统角色定义
"你是行业定义分析引擎。你的任务是：输入行业名称，产出符合行业定义方法论标准的行业定义报告。报告不包含竞争排名、市场规模预测、投资建议。"
⬇️ 分隔线 \n\n---\n\n
LAYER 2
方法论切片
_methodology_slice(step_id) — 按步骤动态加载相关方法论章节
通过 SLICE_MAP 将 step_id 映射到关键词，按 ## / ### 标题切分方法论文档，子串匹配后拼接。空切片或总长度 <100 字符时降级回全量方法论。
⬇️ 分隔线 \n\n---\n\n
LAYER 3
任务指令
★ v4 新增
_task_directive(step_id, industry) — 当前步骤的具体任务指令 + Sprint Contract 验收标准
从 STEP_TASKS 字典获取模板，格式化行业名称。包含：任务描述、输出格式要求、验收标准、严格禁止内容。解决 v3 中任务指令与前序摘要混在一起的模糊问题。
⬇️ 分隔线 \n\n---\n\n
LAYER 4
前序摘要
_previous_summary(state) — 最近 3 步的结果摘要
从 state.steps[-3:] 提取每步的 summary 或 reasoning[:150]，附带置信度标注。让 LLM 了解已完成的上下文，避免重复工作或矛盾输出。
v3 → v4 修复原因：v3 的三层组装丢失了关键的任务指令层，导致 LLM 对当前步骤的具体任务和验收标准理解模糊。v4 将 Sprint Contract 验收标准直接内嵌到每步的 task prompt 中，而非通过独立的 SprintContract 对象传递。
📋
STEP_TASKS 任务指令示例
# Step 1: 信息收集 "请搜索并整理以下行业的基础信息：{industry}。" "要求：覆盖官方定义、关键政策/标准、" "结构性影响因素、相邻行业。" "标注信息来源和可信度（P0-P3）。" "输出 JSON 格式..."
# Step 2: 维度筛选（含验收标准） "基于 Step 1 的信息，对行业「{industry}」" "应用 H1-H4 维度筛选原则。" "选出核心维度，并明确记录：" "选了什么、放弃了什么、为什么。" "验收标准：覆盖 ≥ 2 个独立侧，" "每个维度有经营结果传导。"

Independent Evaluator — 独立评估器
关键约束：Evaluator 只看最终报告文本，不接收 Step 1-4 的 reasoning。把"干活"和"挑刺"彻底分开。
C1
区分度测试
遮住行业名称，读者能否从定义本身判断出是哪个行业？
C2
废话过滤
是否存在对任何行业都成立的通用陈述？
C3
结构性测试
核心逻辑是否独立于短期市场数据？
C4
边界清晰度
读者能否说清楚"什么不是这个行业"？
C5
推理可见
每个关键判断是否有"为什么"的解释？

🧪
Mock 模式评估规则
不调用 LLM，用关键词规则做基本检查（开发测试用）。
C1: 区分度
  • 检查行业名称是否在报告中出现
  • 未出现 → FAIL
C2: 废话过滤
  • 关键词黑名单："市场前景广阔"、"竞争日益激烈"、"具有广阔的发展空间"...
  • 命中 → FAIL
C4: 边界清晰度
  • 检查 "排除" / "不属于" / "边界" 关键词
  • 均未出现 → FAIL
C5: 推理可见
  • 检查 "因为" / "因此" / "所以" / "这意味着" / "依据" / "推理"
  • 均未出现 → FAIL
