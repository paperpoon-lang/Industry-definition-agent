STEP 01 信息收集 — 并行搜索 + FM 审查补搜循环 + LLM 总结 v5.2 新增
输入
  • 行业名称（CLI 参数）
  • Context Builder 四层上下文
  • Tavily API Key（环境变量）
  • 方法论"信息优先级"章节（FM 审查用）
处理逻辑
  • 3 个静态模板搜索（asyncio.gather）
  • FM 审查搜索结果（基于方法论"信息优先级"）
  • 最多 2 轮补搜（每轮 1-2 个 query）
  • 补搜后仍有缺口 → 记录 data_gaps_remaining
  • LLM 总结为结构化 JSON
输出格式（JSON）
  • summary — 行业概述
  • official_definitions — 官方定义
  • key_regulations — 关键政策
  • structural_factors — 结构性因素
  • adjacent_industries — 相邻行业
  • data_gaps — 数据缺口
v5.2 关键约束
  • 搜索补搜循环最多 2 轮，总共 ≤5 个 query
  • 不改 search.py 接口
  • FM 审查基于方法论信息优先级
  • Step 1 timeout: 120s → 180s
# FM_REVIEW_PROMPT（v5.2 新增）— FM 审查搜索结果 "你是行业定义信息完整性审查员。你的任务是判断当前搜索结果是否覆盖了行业定义所需的关键信息维度。 ## 行业 {industry_name} ## 信息优先级（来自方法论） {methodology_info_priority} ## 当前搜索结果摘要 {search_results_summary} ## 你的任务 1. 对照"信息优先级"，判断当前搜索结果是否有明显缺失的维度 2. 如果有缺失，列出具体缺失的维度（data_gaps） 3. 为每个缺失维度生成 1 个补搜关键词（suggested_queries） ## 输出格式（JSON） { "data_gaps": [...], "suggested_queries": [...] }"
# 搜索查询模板（3 个静态模板 + 最多 2 个补搜 query） SEARCH_QUERIES = [ "{industry} 行业定义 官方定义 标准", "{industry} 政策 监管 产业链", "{industry} 边界 与相邻行业区分", ] # 补搜 query 由 FM 审查基于方法论信息优先级动态生成
STEP 02 维度筛选 — H1-H4 原则应用
输入
  • Step 1 的信息收集结果
  • Context Builder 四层上下文
  • 方法论 §3.1 维度筛选原则
处理逻辑
  • 应用 H1：独特形态 / 被极端放大
  • 应用 H2：独立侧（≥2 个）
  • 应用 H3：经营结果传导
  • 应用 H4：数据可获得性
  • 明确记录：选了什么、放弃了什么、为什么
输出格式（JSON）
  • selected_dimensions — 选中维度列表
  • abandoned_dimensions — 放弃维度及原因
  • reasoning — 筛选推理过程
验收标准
  • 覆盖 ≥ 2 个独立侧
  • 每个维度有经营结果传导
  • 放弃维度必须记录原因
# H1-H4 维度筛选原则 H1: 独特形态 / 被极端放大 → 决定行业"长什么样" H2: 独立侧 ≥2 个 → 技术/制度/需求/成本 H3: 经营结果传导 → 每个维度影响商业决策 H4: 数据可获得性 → 合法筛选标准
STEP 03 结构决策 — 报告章节设计
输入
  • Step 2 的维度筛选结果
  • Context Builder 四层上下文
  • 方法论 §3.4 报告结构启发式
处理逻辑
  • 每章对应 Step 2 至少一个维度
  • 严格禁止竞争格局/市场规模/投资建议章节
  • 方法论附注章解释维度取舍
输出格式（JSON）
  • chapters — 章节列表（title, dimensions, summary）
  • reasoning — 结构设计推理
典型结构
  • 一、行业核心定义
  • 二、行业边界划定
  • 三、结构性特征分析
  • 四、制度与监管环境
  • 五、方法论附注
STEP 04 内容生成 — 撰写完整报告
输入
  • Step 3 的章节结构
  • Step 1 的信息收集结果
  • Context Builder 四层上下文
  • 方法论 Hard Rules + 推理展示要求
处理逻辑
  • 直接输出 Markdown（从 # 标题开始）
  • 剥离开场白（_strip_preamble）
  • 每个关键判断附带推理链和置信度
  • 所有数据标注来源和可信度
严格禁止内容
  • ❌ 企业排名 / 市场份额
  • ❌ 竞争格局分析
  • ❌ 市场规模预测
  • ❌ 投资建议
输出格式
  • Markdown 完整报告
  • 存储于 step.result.report_text
  • 最长步骤（15-35 秒）
瓶颈步骤：Step 4 是端到端最大瓶颈，长报告可能需要 90 秒。建议演示时预先运行保存结果。
STEP 05 自检 — Independent Evaluator
输入
  • Step 4 生成的报告文本（仅最终文本）
  • 行业名称
  • 不接收 Step 1-4 的 reasoning
处理逻辑
  • 独立 LLM 调用（不同 prompt）
  • C1-C5 逐项审查
  • 每个维度 PASS/FAIL + 具体问题
  • 总体：pass / fail_with_fixes
输出格式（JSON）
  • overall — pass / fail_with_fixes
  • evaluator_confidence — high/medium/low
  • dimensions.C1-C5 — status + detail
  • failed_dimensions — 未通过列表
  • issues — 具体问题
  • fixes_required — 修复建议（v5 设计笔记预留）
v5 新增
  • Step 5 产生降级时记录 quality_flags
  • fixes_required 设计笔记为阶段三 Evaluator-Optimizer 闭环预留接口
设计意图：把"干活"和"挑刺"彻底分开。Evaluator 是独立的审查员，倾向于发现问题而非确认一切正常。这是解决 Self-Evaluation Bias 的核心机制。
STEP 06 输出 — 组装最终报告
输入
  • Step 4 报告正文
  • Step 5 自检结果（若失败）
  • 各步骤 quality_flags 降级记录
处理逻辑
  • 自检通过 → 直接输出报告
  • 自检失败 → 头部注入 ⚠️ 警告
  • 尾部注入 quality_flags 汇总（按 high/medium/low 分组）
  • 方法论附注（R5 强制要求）
  • 安全保存（UTC 时间戳 + 版本号）
报告尾部结构（v5.1）
  • 报告正文
  • → 自检未通过（如有，最高优先级）
  • → 降级记录（quality_flags，如有，次高优先级）
  • → 方法论附注（最后）
v5 变更
  • 移除 尾部附加 Token 统计（Token 统计移到独立 TokenAudit）
  • 新增 quality_flags 汇总注入
  • Output Safety：UTC 时间戳 + 版本号
# 报告尾部结构（v5.1） [报告正文] --- ## ⚠️ 自检未通过（如有，最高优先级） --- ## ⚠️ 降级记录（quality_flags，如有，次高优先级） ### 高严重度 ### 中严重度 ### 低严重度 --- ## 方法论附注（R5 强制要求，最后）

Context Builder — 四层上下文组装器
v4 核心改进：新增"任务指令层"（Layer 3）。v5 继承四层结构，不变。
LAYER 1
静态身份
_static_identity() — 固定不变的系统角色定义
"你是行业定义分析引擎。你的任务是：输入行业名称，产出符合行业定义方法论标准的行业定义报告。报告不包含竞争排名、市场规模预测、投资建议。"
⬇️ 分隔线 ---
LAYER 2
方法论切片
_methodology_slice(step_id) — 按步骤动态加载相关方法论章节
通过 SLICE_MAP 将 step_id 映射到关键词，按 ## / ### 标题切分方法论文档，子串匹配后拼接。空切片或总长度 <100 字符时降级回全量方法论。
v5 升级：优先从拆分模块加载，_meta.yaml 声明模块清单。
⬇️ 分隔线 ---
LAYER 3
任务指令
★ v4 新增 · v5 继承
_task_directive(step_id, industry) — 当前步骤的具体任务指令 + Sprint Contract 验收标准
从 STEP_TASKS 字典获取模板，格式化行业名称。包含：任务描述、输出格式要求、验收标准、严格禁止内容。解决 v3 中任务指令与前序摘要混在一起的模糊问题。
⬇️ 分隔线 ---
LAYER 4
前序摘要
_previous_summary(state) — 最近 3 步的结果摘要
从 state.steps[-3:] 提取每步的 summary 或 reasoning[:150]，附带置信度标注。让 LLM 了解已完成的上下文，避免重复工作或矛盾输出。
v3 → v4 修复原因：v3 的三层组装丢失了关键的任务指令层，导致 LLM 对当前步骤的具体任务和验收标准理解模糊。v4 将 Sprint Contract 验收标准直接内嵌到每步的 task prompt 中，而非通过独立的 SprintContract 对象传递。v5 继承此设计，未改变四层结构。

Mock 模式评估规则
不调用 LLM，用关键词规则做基本检查（开发测试用）。
C1: 区分度
  • 检查行业名称是否在报告中出现
  • 未出现 → FAIL
C2: 废话过滤
  • 关键词黑名单："市场前景广阔"、"竞争日益激烈"、"具有广阔的发展空间"...
  • 命中 → FAIL
C4: 边界清晰度
  • 检查 "排除" / "不属于" / "边界" 关键词
  • 均未出现 → FAIL
C5: 推理可见
  • 检查 "因为" / "因此" / "所以" / "这意味着" / "依据" / "推理"
  • 均未出现 → FAIL

🚩 quality_flags
v5 新增

实现文件：models.py

核心功能：Pydantic 模型约束，跨步骤异常传递。降级信息不消失在状态对象中，按 high/medium/low 严重度分组汇总到报告尾部。

关键约束：category 预定义值可扩展，但新增需登记；or_fallback 拆分为 result（high）和 reasoning（medium）。

v5 升级

实现文件：harness/session_log.py

核心功能：JSONL 持久化，append-only，trace_id 注入（Orchestrator 统一生成），降级到 print 不崩溃。

关键约束：签名兼容 v4 SimpleLogger；目录创建失败也降级。

💰 Token Audit
v5 新增

实现文件：harness/token_audit.py

核心功能：持久化报表（JSON + Markdown），CLI 成本摘要。不改变 StepOutput 模型。

关键约束：定价来源明确标注（SiliconFlow 官网）；文件名含 trace_id。
