## 一、当前状态

### 1.1 当前补搜逻辑（frost_agent.py L442-L609）

```
首轮 3 个静态模板搜索
  → FM 审查（检查信息缺口 + 生成补搜关键词）
  → 循环：最多 2 个补搜 query（硬编码 MAX_SUPPLEMENT_QUERIES=2）
  → 最终审查（补搜后再审查一次）
  → 记录 data_gaps_remaining（medium，不终止）
```

### 1.2 当前问题（已经 2026-08-14 日志诊断确认，证据见评议文档第七节）

5/5 行业（2026-06-27 批次）补搜后仍有 1-4 个信息缺口。诊断确认的三个关键事实：

1. **"上限 2"的真实语义是"只允许 1 轮补搜"**：MAX_SUPPLEMENT_QUERIES 数的是 query 数，而 FM 每轮固定建议 2 个 query，首轮补搜即耗尽预算（5 个行业均 query_count=5 = 初始 3 + 补搜 2）。
2. **唯一的 1 轮补搜在 5/5 行业都是有效的**：原缺口全部闭合或被显著细化，但最终审查又发现新缺口（"换口不缩量"）——瓶颈是轮次不够，不是搜索无效。
3. **FM 攥着线索被迫停下**：5 个行业的最终审查全部给出了未被执行的 suggested_queries。

根因：固定上限是"预算决定停止"——不管信息缺口是否闭合、不管继续搜还有没有收益、不管 FM 是否还有未试动作，到限就停。

### 1.3 当前 data_gaps_remaining 的记录格式

```python
QualityFlag(
    category="data_gaps_remaining",
    field="data_gaps",
    severity="medium",
    detail=f"补搜 {supplement_queries_used} 个 query 后仍有缺口: {'; '.join(fm_result['data_gaps'])}",
)
```

只记录了"补搜了几个 + 缺口名称列表"，没有记录"搜了什么 query、搜到了什么、为什么缺、为什么停"。

### 1.4 已确认的既有行为（团队 2026-08-14 确认）

- **FM 审查失败时**（frost_agent.py L534-537）：记录 `fm_review_skipped` flag + break 跳出补搜循环。非 raise。本方案的 `fm_review_failed` stop_reason 是**补记既有行为**，不是新增能力。

## 二、设计目标

**让系统自动判断更聪明，不依赖用户手动干预。**

- 停止条件从"预算驱动"升级为"证据驱动"
- 缺口记录从"缺口名称列表"升级为"结构化终态记录"（机器信号走 Event Log，人读文本走 QualityFlag，两通道分离）
- 为阶段三 Evaluator-Optimizer 闭环预留输入信号
- **接受"有些缺口永远闭不了"为正常产出**（团队已确认）：信息确实不存在时，诚实声明"搜不到"优于编造数据

## 三、迭代方案

分 3 步迭代，每步可独立实施和验证，不依赖后续步骤。

### 步骤 1：补搜停止逻辑升级——FM 自评收益 + 双信号判断

**改动文件**：`demo2/frost_agent.py`（`step1_search_with_supplement` 函数 + FM 审查 prompt）

**停止条件总表**：

| stop_reason | 含义 | 触发条件 |
|-------------|------|---------|
| `gaps_closed` | 缺口全部闭合 | FM 返回 data_gaps 为空 |
| `low_yield` | 期望收益止损 | FM **连续 2 轮**判定 `last_round_yield="unproductive"` |
| `budget_exhausted` | 预算用尽 | 补搜轮数 >= `MAX_SUPPLEMENT_ROUNDS`（默认 3） |
| `fm_review_failed` | FM 审查失败 | timeout/parse_error/exception（**补记既有行为**：L534-537 现为记 flag + break） |
| `no_suggested_queries` | FM 未生成补搜关键词 | suggested_queries 为空 |

**FM 审查 JSON schema 扩展**（新增一个字段，不破坏现有结构）：

```json
{
  "last_round_yield": "productive | unproductive",
  "data_gaps": ["..."],
  "suggested_queries": ["..."]
}
```

- 首轮审查无上一轮，`last_round_yield` 缺省或置 null，不参与判断。
- 从第 2 轮审查起，FM 必须对上一轮补搜的收益做出判定。

**FM prompt 中 unproductive 的判定标准**（团队要求明确定义，防 LLM 自我确认偏差）：

> `last_round_yield` 判定标准（第 2 轮起必填）：
> - `"productive"`：上一轮补搜为**至少一个**缺口带来了相关新信息。以下都算有进展——缺口被闭合；缺口被细化（颗粒度更细、更具体）；发现了与缺口相关的新事实。**注意：缺口数量不变不代表无收益，缺口内容变化也算有进展。**
> - `"unproductive"`：上一轮补搜的返回结果与所有缺口均无关，或只是重复已知信息，没有任何缺口因此获得新内容。
> 判定必须保守：只有当上一轮搜索**完全没有**带来任何缺口相关的新信息时，才判 unproductive。

**止损伪代码**：

```python
consecutive_unproductive = 0

# 循环内，FM 审查返回后：
data_gaps = fm_result.get("data_gaps", [])
if not data_gaps:
    stop_reason = "gaps_closed"
    break

yield_flag = fm_result.get("last_round_yield")  # 首轮为 None
if yield_flag == "unproductive":
    consecutive_unproductive += 1
else:
    consecutive_unproductive = 0  # productive 或首轮都重置

if consecutive_unproductive >= 2:
    stop_reason = "low_yield"
    break

if supplement_rounds_used >= MAX_SUPPLEMENT_ROUNDS:
    stop_reason = "budget_exhausted"
    break

suggested = fm_result.get("suggested_queries", [])
if not suggested:
    stop_reason = "no_suggested_queries"
    break
# 执行本轮补搜（suggested_queries 全部执行，通常 2 个）
```

**为什么用 FM 自评而非事后 diff 文本列表**（v1.0 计数判据被否决的记录）：

v1.0 曾设计"补搜后 gap 计数不减则止损"。2026-08-14 用 5 行业真实日志回放该判据：4/5 行业补搜后计数不变（2→2）但原缺口全部闭合（换口不缩量——补搜有效、新缺口浮现），判据会在第 1 轮误触发止损，预算调大的收益被完全抵消。FM 自评让 LLM 在审查当下利用领域上下文判断收益，绕开文本表述漂移问题。残余风险：LLM 可能倾向说 productive（自我确认偏差）——靠 prompt 中"必须保守"的判定标准约束，并在集成测试中观察 low_yield 的实际触发频率来校验。

**工作量**：3-5h（含 FM prompt 调整与 schema 解析兼容）

### 步骤 2：缺口记录增强——双通道结构化终态 + 补搜过程采集

**改动文件**：`demo2/frost_agent.py`（`step1_search_with_supplement` 函数末尾 L589-L597 + 补搜循环内）

**设计原则（v1.1 修正）**：人读文本与机器信号分离——

- `QualityFlag.detail` **保持人读纯文本**，格式不变式升级：
  ```python
  detail = (
      f"补搜 {supplement_rounds_used} 轮（{supplement_queries_used} 个 query）后仍有 "
      f"{len(remaining_gaps)} 个缺口: {'; '.join(remaining_gaps)}；停止原因: {stop_reason}"
  )
  ```
  `category`/`field`/`severity` 均不变，Step 6 下游消费方零适配。

- 结构化 `gap_record` 写入 **Session Event Log**（JSONL 通道，trace_id 可关联，给阶段三循环系统消费）：
  ```python
  logger.log("search_gap_record", {
      "queries_used": list(all_results.keys()),
      "supplement_rounds": supplement_rounds_used,
      "supplement_queries": supplement_queries_used,
      "remaining_gaps": remaining_gaps,
      "stop_reason": stop_reason,
      "yield_history": yield_history,  # 每轮 FM 的 last_round_yield 判定序列
  })
  ```

**新增采集（诊断基础，成本极低）**：补搜循环内每轮记录——

```python
logger.log("supplement_search_done", {
    "round": round_idx,
    "queries": queries_this_round,
    "results_per_query": {q: len(all_results.get(q, [])) for q in queries_this_round},
    "content_lengths": {q: sum(len(r.get("content","")) for r in all_results.get(q, [])) for q in queries_this_round},
})
```

这是本次日志诊断暴露的采集缺口（Tavily 返回与补搜执行记录均未入日志，诊断只能靠缺口流转间接推断），是后续所有搜索策略迭代的诊断基础。

**用途**：
- 现阶段：开发调试——理解每种 stop_reason 的频率和对应缺口特征
- 阶段三：Evaluator-Optimizer 循环的输入——`low_yield` 可能触发"换搜索策略"而非"继续搜"

**工作量**：2-2.5h（含新增采集）

### 步骤 3：补搜 query 质量评估（可选，视效果决定）

**前提**：步骤 1-2 实施后，跑 5 行业实测，观察 stop_reason 分布与 `supplement_search_done` 采集数据。如果 `low_yield` 频繁出现且缺口仍然重要，再考虑步骤 3。

**改动文件**：`demo2/frost_agent.py`（补搜循环内，L558-L570）

**增强**：在补搜后评估搜索结果质量，作为"期望收益"的第二维度：

```python
new_results_count = sum(1 for q in queries_to_search if len(all_results.get(q, [])) > 0)
new_results_content_length = sum(
    len(r.get("content", ""))
    for q in queries_to_search
    for r in all_results.get(q, [])  # 遍历该 query 的全部结果，而非只取第一条（v1.0 写法修正）
)
if new_results_count == 0 or new_results_content_length < 100:
    low_quality_rounds += 1
    if low_quality_rounds >= 2:
        stop_reason = "low_yield"
        break
else:
    low_quality_rounds = 0
```

**若步骤 3 实施**：`low_yield` 届时细分子类（`low_yield:fm_judged` / `low_yield:empty_results`），写入 Event Log 的 gap_record（QualityFlag.detail 人读文本不变）。v1.1 阶段不细分（团队决定）。

**工作量**：1-2h

**风险**：内容长度不等于内容质量。100 字符的阈值是经验值，用步骤 2 采集的 `content_lengths` 实际分布来校准，不拍脑袋。

用 5 行业真实 API 跑一遍。**KPI 已按团队确认修正**（接受"有些缺口永远闭不了"为正常产出）：

| 指标 | 预期 |
|------|------|
| stop_reason 分布 | gaps_closed 和 budget_exhausted 占主体；low_yield 可能出现但不应占多数（若占多数，说明 FM prompt 的 unproductive 定义过松或过紧，需校准） |

## 五、环境变量汇总

| 变量 | 默认值 | 说明 |
|------|--------|------|
| ~~`MAX_SUPPLEMENT_QUERIES`~~ | ~~2~~ | **废弃**（数 query 的语义已被证实误导：FM 每轮固定 2 query，上限 2 = 只允许 1 轮） |
| `MAX_SUPPLEMENT_ROUNDS` | 3（新增） | 补搜**轮数**上限（每轮执行 FM 建议的全部 query，通常 2 个） |
| `MAX_TOTAL_QUERIES` | 10（原 5） | 总 query 上限（初始 3 + 补搜 3 轮 × 2 = 9 < 10，保留为防 FM 单轮建议数膨胀的安全网） |
| `FM_REVIEW_TIMEOUT` | 60（不变） | FM 审查单次超时 |
| `SEARCH_PHASE_TIMEOUT` | **400（从 300 上调，团队确认）** | 搜索阶段整体兜底超时 |

**超时最坏情况核算**（v1.1 重算，审查次数函数关系已写明）：

- 审查次数 = 首次 1 + 每补搜轮 1 + 最终 1，预算 3 轮 ⇒ 最多 5 次
- 最坏 = 首轮搜索 ~16s + 5 × 60s（FM 超时值）+ 6 个补搜 query × ~8s ≈ **364s < 400s** ✅

## 七、未覆盖的（显式声明）

- **白名单深评**：不做。当前 Tavily API 不支持逐页深评。等阶段三接入非碎片化搜索源后重新评估。

- **跨会话档案复用**：不做。属于阶段三 Persistent Memory 范畴。
- **FM 审查能力升级**（从"检查缺口"到"枚举未试动作"）：部分缓解——FM 的 suggested_queries 已是"未试动作"雏形且新方案会消费它们；但完整的动作枚举不做，等阶段三 Model Router 引入后评估。
