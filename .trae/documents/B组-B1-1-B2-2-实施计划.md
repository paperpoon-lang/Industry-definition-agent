## 一、背景摘要

A 组 P0-1 根因是 `_check_quality_gate` 硬编码 `category == "or_fallback_result"` 作为终止条件。新增 `search_phase_timeout` 时终止条件未同步，导致 A 组只能绕过 `_check_quality_gate` 直接在 `_run_step1` 中 raise。这形成了 SSOT 反模式：未来每新增一个需终止的 high category 都要手动维护 raise 点。

B1-1 目标：在 `QualityFlag` 新增 `terminates_flow` 元数据字段，`_check_quality_gate` 统一扫描 `severity == "high" and terminates_flow == True` 决定是否终止。消除 A 组留下的直接 raise。

B2-2 目标：补充 A 组缺失的降级路径集成测试，验证 `search_phase_timeout` 触发后 JSONL 日志、checkpoint 文件、token_audit 的联动正确性。

**v1.2 修正**：原计划新增 `CATEGORY_TERMINATES_FLOW: set[str]` 静态集合作为"文档性注释"。architecture-critic 指出这是 SSOT 反模式的另一种形式——集合"不参与运行时"却需手动同步，新增 category 漏改=审计盲区，与硬编码 category 同病。删除该集合。

#### d) 新增 model_validator 不变量（v1.2 新增，采纳 architecture-critic P1 建议）

`terminates_flow=True` 但 `severity="medium"` 时 `_check_quality_gate` 会静默不终止，潜伏 bug。添加 validator 强制不变量：

```python
@model_validator(mode="after")
def _check_terminates_flow_consistency(self) -> "QualityFlag":
    """B1-1 新增：terminates_flow=True 时强制 severity='high'。

    防止开发者误设 terminates_flow=True 但 severity=medium 导致 _check_quality_gate 静默不终止。
    """
    if self.terminates_flow and self.severity != "high":
        raise ValueError(
            f"terminates_flow=True 时 severity 必须为 'high'，"
            f"实际为 '{self.severity}'。terminates_flow 表示触发流程终止，"
            f"仅 severity='high' 时 _check_quality_gate 才会扫描。"
        )
    return self
```

```python
def _check_quality_gate(step_output: StepOutput, step_id: str) -> None:
    """B1-1 重构：基于 terminates_flow 元数据统一判断终止条件（SSOT）。

    替代原来硬编码 category == 'or_fallback_result' 的方式。
    任何 flag 设置 terminates_flow=True 且 severity='high' 时触发终止。

    Args:
        step_output: 刚完成的步骤输出
        step_id: 步骤标识

    Raises:
        QualityGateError: 当 step_output.quality_flags 含任何 terminates_flow=True 的 flag 时

    if step_id not in PRODUCTION_STEPS:

                f"步骤 {step_id} 触发终止性降级：{flag.category}/{flag.field} — {flag.detail}。"

            )
```

## 六、风险与边界

### B1-1 风险
- **测试 adapter cost**：`test_search_phase_timeout_cascade` 和 `test_search_partial_failure_plus_timeout_cascade` 两个测试的 `pytest.raises(match=...)` 需要更新匹配模式，工作量 <30min
- **`will_terminate` 表达式同时承担"跳过 LLM"和"决定终止"两个职责**：v1.1 修正后，该表达式与 `_check_quality_gate` 的扫描逻辑 DRY。但需注意：若未来某 flag 设 `terminates_flow=True` 但语义上仍想调用 LLM（如"降级但可继续"场景），需重新拆分职责。当前所有 `terminates_flow=True` 的 flag 语义都是"无法继续"，无此风险
- **Step 1 两个 flag 设置点需额外小心**：`search_phase_timeout`（except 分支）和 `search_partial_failure(all_queries)`（步内函数）都需设 `terminates_flow=True`，不可遗漏

### B2-2 风险
- **测试使用 `tmp_path`**：需确认 CI 环境支持 pytest 的 `tmp_path` fixture（标准 fixture，无需额外依赖）
- **B2-2 依赖 B1-1**：若 B1-1 未完成，B2-2 测试无法通过（`terminates_flow` 字段缺失）
- **JSONL 验证复杂度**：JSONL 行数取决于 mock 精确度，建议使用宽松断言（存在性检查），避免过度约束行数
