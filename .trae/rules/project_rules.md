# 行业定义 Agent — 项目规则

> 对 Trae（AI 助手）的行为约束。每次任务自动加载。

---

## 规则 1：事实性数据必须带来源

产出含数字/日期/版本号/技术参数/产品名/性能数据的文档时：
- 每个数字标注来源（URL + 日期 + 可信度）
- 可信度 ≤ ★★☆☆☆ 必须在正文写"此数据仅来自单一来源/为推理结果，建议验证"
- 严禁用精确小数伪装确定性——只有大概范围就说"约"或"据称"

可信度五级：

| 级别 | 来源类型示例 |
|------|------------|
| ★★★★★ | 学术论文（arXiv）、官方 GitHub README、官方文档 |
| ★★★★☆ | 权威媒体（Reuters/VentureBeat）、官方博客 |
| ★★★☆☆ | 技术博客分析、社区反向工程 |
| ★★☆☆☆ | 单一来源无法交叉验证 |
| ★☆☆☆☆ | 推理得出，非事实 |

产出后用 FactChecker Agent 核查。

---

## 规则 2：不确定就说不知道

搜索不到确切来源、来源矛盾、信息过时时：
- 写"来源不明，需人工确认"比编合理数字好一万倍
- 技术名词以官方文档/源码为准，不自创命名
- 版本号交叉验证，不只看文件名

---

## 规则 3：架构评估必须先定义框架

产出架构评估/对比文档时：
- 先写评估框架再展开：评估维度 + 权重 + 评级标准(A/B/C/D/F) + 信息来源可信度
- 框架写完后用 ArchitectureCritic 审查框架本身

❌ 直接跳到对比 / 给 Demo 原型打 90-95 分

---

## 规则 4：工程视角强制覆盖

评估 Agent 架构时，五个问题必须回答（即使粗略估算）：
- 成本：单次 API 调用次数、Token 消耗、大致费用
- 延迟：串/并行步骤数、端到端时间
- 错误处理：LLM 格式错误/API 限流/超时怎么办
- 恢复机制：进程崩溃后能否从中间步骤恢复
- 并发：是否支持同时多任务

---

## 规则 5：代码建议必须具体

每条代码建议必须含：文件名 + 伪代码/函数签名 + 预估工作量(<1h/2-4h/1-2d/>2d) + 优先级(P0/P1/P2)

---

## 规则 6：文件修改前必须先读

- 修改已有文件 → 先用 Read 完整读取
- 新建文件 → 先确认父目录存在
- 不要没读过就说"我应该知道里面有什么"

---

## 规则 7：术语和版本统一

- 同一概念全文只用同一个术语
- 版本号连贯一致，涉及多文档时交叉验证
- 不确定版本号标注"待确认"

---

## 规则 8：批判性思维的最低门槛

产出评估类文档时，先回答三个问题：
1. 这个架构能否通过最基础的测试（不是设计好不好，是能不能跑）
2. 如果部署到生产环境，第一个故障会是什么
3. 放弃这个架构失去什么、选择它失去什么

回答不了说明没真正理解 trade-off。

---

## 规则 9：质量门

**触发条件**：用 Write/Edit 产出或修改 `.md` 文件时，new_str 行数 > 80 行（含替换行）。

必须通过以下检查才能交付：
- [ ] 全文至少 1 个来源脚注（带 URL 和日期）
- [ ] 所有数字标注了可信度或"待验证"
- [ ] 术语全文统一
- [ ] 没有"查无来源"的精确数字
- [ ] 评估类文档：评估框架 → 逐项打分 → 总结，三段式结构完整

任何一项不通过，不交付。自行校对后重新输出。

---

## 规则 10：审查 Agent 调用

### 10.1 文档产出类审查

| 内容类型 | Agent | 用途 |
|---------|-------|------|
| 技术数据的准确性 | `ai-architecture-fact-checker` | 交叉验证数字、日期、技术参数、版本号 |
| 架构评估的客观性 | `architecture-critic` | 找出薄弱环节、过度乐观、工程遗漏 |

**调用时机**：>80 行 `.md` 产出后，向用户汇报**之前**调用。等完整初稿出来再核查，不要每段都调。

### 10.2 代码改动类审查

| 改动类型 | Agent | 时机 |
|---------|-------|------|
| 修改 `models.py` 任何字段 | `architecture-critic` | Edit **之前**（审设计）+ **之后**（审实现） |
| 修改 state 在步骤间的传递逻辑 | `architecture-critic` | Edit **之前** |
| 新组件实现完成 | `agent-code-validator` | 写入文件后、汇报**之前** |

**"实现完成"的定义**（同时满足）：
1. 接口定义明确（签名稳定）
2. Mock 测试通过（需有持久化 test 文件，非临时脚本）
3. 真实 API 测试通过（如组件依赖外部 API）
4. 代码已写入文件

> 组件依赖未就绪时允许 Mock 版本，验证时标注 `#[mock]`，等依赖就绪后补做完整验证。
> 同一次改动涉及多个触发条件时，合并为一次调用，不重复审查。

### 10.3 汇报前强制检查清单

每次向用户发文本汇报前过以下检查。任何一项"是"但 Agent 未调，**不汇报，先调**。

**文档类**：
- [ ] 本次产出/修改 >80 行 `.md`（含替换行）？→ 已调 fact-checker + architecture-critic？
- [ ] 文档含技术数据？→ 已调 fact-checker？

**代码类**：
- [ ] 本次修改了 `models.py` 字段？→ Edit 前已调 architecture-critic？
- [ ] 本次修改了 state 传递逻辑？→ Edit 前已调 architecture-critic？
- [ ] 本次有新组件实现完成？→ 已调 agent-code-validator？

例外：纯对话回复无需过此清单。

### 10.4 Agent 推荐路由表（非强制）

> agent 选型时过一遍，确认无遗漏。

| 场景 | 推荐 agent | 用途 |
|------|-----------|------|
| 产出 >80 行 .md | `ai-architecture-fact-checker` | 交叉验证技术数据 |
| 修改 models.py | `architecture-critic` | 审查字段变更影响 |
| 新组件实现完成 | `agent-code-validator` | 运行时验证 |
| Step 5 自检持续 fail | `methodology-expert` | 分析是否方法论应用问题 |
| 方法论版本升级后 | `methodology-expert` | 检查新规则是否生效 |
| 批量测试后质量检查 | `definition-quality-checker` | 验证输出语义质量一致性 |
| 从零实现新模块 | `python-backend-implementer` | 生成骨架代码 |
| 代码变更完成后 | `frost-test-runner` | 回归测试 |

## 规则 11：采纳外部 agent 建议前的去偏见化

**触发条件**：采纳任何 agent（含外部如 Kimi、内部 subagent）的建议时。

**规则**：
1. 验证该建议的技术前提（用 grep/read 核对代码事实，不能只凭 agent 论证）
2. 多方案选择时，说明为什么选这个而不是其他
3. 未采纳的建议在产出文档中记录反驳理由
4. 有可反驳之处就列，没有就说"经验证无反驳点"

核心：不要全盘接受，也不要为了反驳而反驳。关键是验证前提 + 说明选择理由。

**自检清单**（采纳前过一遍）：
- [ ] 这条建议的技术前提我用 grep/read 验证过吗？
- [ ] 多方案可选时我为什么选这个？
- [ ] 没采纳的建议我记录反驳理由了吗？

❌ "Kimi 的评议很有价值，全部采纳"——没验证前提，没说明选择理由
❌ 默默跳过 agent 提出的需要团队反馈的问题，替用户做决定

---

## 规则 12：多 agent 意见冲突时的仲裁原则

**触发条件**：两个或以上 agent 对同一问题给出不一致建议。

**仲裁优先级**：
1. **代码事实优先**：以 grep/read 直接验证的结果为准，非 agent 论证
2. **已确认根因为准**：开发日志记录的根因 > 新 agent 的假设
3. **工程权衡明确化**：无法事实仲裁时，列出 trade-off 表格，由人类决策
4. **保守原则**：不确定时选更简单、更少改动的方案
