
# 架构设计借鉴来源与取舍说明

> 版本：v1.0 | 日期：2026-06-05
>
> 本文档追溯行业定义 Agent 架构设计（v4 Demo MVP + 演进路线图 v2）
> 对现有优秀 Agent 系统的借鉴，说明借鉴原因，并区分直接采纳、有取舍地改动、
> 以及针对本项目独立设计的部分。

---

## 一、概述

行业定义 Agent 的架构设计不是从零开始的。在从项目 Brief → v1 → v2 → v3 → v4 的迭代过程中，我们系统性地研究了三套成熟 Agent 系统的设计模式（Claude Code、Anthropic Harness、Hermes Agent），并针对"Demo MVP"的定位做了以下核心取舍：

- **借鉴什么**：解决通用 Agent 工程问题的成熟模式（如何组织上下文、如何避免自评偏差、如何处理错误）
- **不借鉴什么**：为生产级系统设计的重型基础设施（分布式审计管道、Docker 隔离、多模型降级链）
- **独立设计什么**：行业定义方法论特有的需求（六步管线、按步骤的方法论切片注入、Demo 范围裁剪的"做/打桩/不做"框架）

## 三、逐项借鉴说明

### 3.1 Claude Code — Context Builder 分层组装

**来源**：Claude Code 的 System Prompt 是 18 层分层结构（arXiv:2604.14228v1 详细分析了其组装逻辑），核心原则是"静态放前、动态放后、最高权重指令放最后以利用模型的 recency bias"。

**我们借鉴了什么**：按层次组装 LLM 上下文的思路——尤其是"方法论切片作为中层、具体任务指令作为高层"的分层哲学。

**为什么借鉴**：项目 Brief 约束 #5 要求"方法论文档作为外部文件加载，不硬编码在 prompt 里"。如果每个步骤都把完整的方法论（~5000 字）塞进 prompt，不仅浪费 token，还会让当前步骤的无关规则干扰模型推理。分层组装是解决这个问题的自然方案。

**我们的改动（取舍）**：
- Claude Code 是 18 层，我们简化为 **4 层**（静态身份 → 方法论切片 → 任务指令 → 前序摘要）
- Claude Code 的多层中有大量服务于工具调用、权限管理、安全策略的层——我们的 Agent 不执行系统命令、不需要权限控制，这些层全部省略
- v3 曾退化为 3 层（丢掉了任务指令层），v4 基于架构评审修复为 4 层——这是评审中发现的确切问题

**改动理由**：Demo 不需要 Claude Code 的生产级复杂度。但 4 层（而非 3 层）是 v4 评审后确认的最小正确集合——缺了任务指令层，LLM 不知道当前步骤具体该做什么。

---

### 3.2 Claude Code — 搜索并行 + 结果渐进压缩

**来源**：Claude Code 实现了 `isConcurrencySafe()` 标记机制和三级渐进压缩流水线（Budget Reduction → Snip → Summarize），用于在 SubAgent 并行搜索时控制上下文膨胀。

**我们借鉴了什么**：
1. 搜索 query 并行执行（3 个 Tavily 搜索同时发出）
2. 结果截断压缩（单条结果超过 1500 字符截断）
3. 搜索全失败降级策略

**为什么借鉴**：项目 Brief 约束 #4 要求"搜索至少 3 轮，覆盖行业定义 + 政策标准 + 边界争议"。如果没有并行，串行 3 轮搜索的延迟（15-30 秒）在 Demo 演示时会很尴尬。并行可以将延迟降到 3-8 秒。

**我们的改动（取舍）**：
- Claude Code 是三级渐进压缩，我们只有一级（截断）。Demo 不需要完整的优先级丢弃和 LLM 摘要生成——1500 字符截断对于行业定义收集已经足够
- 没有实现 `isConcurrencySafe()` 的正式标记（搜索是只读操作，天然安全）
- 没有实现结果去重（3 个不同方向的 query 返回相同 URL 的概率低）

**改动理由**：Demo 的信息收集量级（3 个 query → 约 30 条结果）远小于 Claude Code 的 SubAgent 探索量级。完整的三级压缩在大规模场景下才有意义。

---

### 3.3 Claude Code — Circuit Breaker

**来源**：Claude Code 实现了完整的 Circuit Breaker 模式（CLOSED/OPEN/HALF_OPEN 三态 + 恢复超时），用于防止重试风暴。核心原则是"没有 Circuit Breaker 的重试不是重试，是自杀"。

**我们借鉴了什么**：Circuit Breaker 的设计思想——连续失败后断路、恢复超时后探测。

**我们的改动（取舍）**：
- v4 Demo 阶段：**打桩为 `call_with_retry()`**——只做指数退避重试（max 3 次），不做状态机
- 路线图阶段二：升级为完整 Circuit Breaker（状态机 + 按操作类型分组）
- 保留了函数签名兼容性（`call_with_retry(fn)` → `CircuitBreaker.call(fn)`），确保升级时不破坏调用方

**改动理由**：Demo 场景下一次运行只有 5-6 个 LLM 调用。单次失败概率低，连续失败概率极低。完整状态机在这类小规模场景下是过度设计。但接口留下了，未来要升级只需替换实现。

---

### 3.4 Anthropic Three-Agent Harness — Independent Evaluator

**来源**：Anthropic 2026 年发表的"Three-Agent Harness"架构将 Agent 分为 Generator、Evaluator、Refiner 三个独立实例。核心发现：同一个 LLM 生成内容后自己检查，存在系统性偏差——模型倾向于对自产内容过度乐观（Self-Evaluation Bias）。

**我们借鉴了什么**：
1. Evaluator 独立化：Step 5 使用独立的 LLM 调用实例，独立的 system prompt
2. Evaluator 不看生成过程的 reasoning，只看最终报告文本
3. Evaluator 的 system prompt 定位为"挑剔的审查员"

**为什么借鉴**：项目 Brief 验收标准要求"Step 5 自检能全部 pass"。如果生成和审查用同一个 LLM 实例，通过率会虚高——不是报告真的好，而是模型不愿否定自己的输出。独立 Evaluator 用一次额外 API 调用的成本换取了自检结果的真实性。

**我们的改动（取舍）**：
- Anthropic 是三 Agent（Generator + Evaluator + Refiner），我们是**单 Agent + 独立 Evaluator**——不走 Refiner 闭环
- v4 **不做 Evaluator-Optimizer 自动修正**。Step 5 失败时，不自动回到 Step 4 重跑，而是把失败维度和问题列表注入报告头部作为警告标记
- Anthropic 的 Evaluator 和 Generator 使用不同模型；我们 Demo 阶段可能同模型（但不共享上下文）

**改动理由**：项目 Brief 约束 #3 说的是"不通过则标记，不允许直接输出"——这是人工审查触发点，不是自动重试。自动修正闭环改变了这个行为契约。我们保留了 Independent Evaluator 的质量价值（独立审查），但拒绝了自动修正的流程改变。

---

### 3.5 Anthropic Managed Agents — Session Event Log / Harness 分层

**来源**：Anthropic 2026 年 Managed Agents 架构提出了 Session Event Log（JSONL 追加写入 + 崩溃恢复）和 Harness/Environment 分层思想。核心认知："Session 是账本，Context 是工作区。"

**我们借鉴了什么**：
1. Session Event Log 的设计：每步执行追加事件，进程崩溃后从日志恢复
2. Harness（控制面）/ Environment（执行边界）分层思想
3. Checkpoint 机制：每步完成后持久化 State

**为什么借鉴**：虽然 Demo 是单次 CLI 运行，但"跑到 Step 4 崩溃后重跑不需要重新搜索"对于演示体验和开发调试都有价值。

**我们的改动（取舍）**：
- v4 Demo 阶段：全部 **打桩**。Event Log → `SimpleLogger`（print 到 stdout），Checkpoint → `save_checkpoint()`（单文件覆盖写入）
- 路线图阶段二：升级为 JSONL 结构化 + 多版本 Checkpoint
- 路线图阶段四：升级为生产级审计管道（ELK/ClickHouse）

**改动理由**：Demo 不需要审计链和分布式查询。但接口留下了——`SimpleLogger.log()` 和 `SessionEventLog.log()` 签名兼容，未来替换实现即可。

---

### 3.6 Hermes Agent — Model Router / Persistent Memory

**来源**：Hermes Agent（Nous Research）实现了三层记忆系统（Working / Episodic / Semantic）和按任务类型路由到不同模型的成本优化策略。

**我们借鉴了什么**：
1. Model Router 思想：不同认知任务（信息提取 vs 推理 vs 长文生成）使用不同能力的模型
2. Persistent Memory 思想：跨运行的行业知识复用

**我们的改动（取舍）**：
- Model Router：v4 Demo 阶段 **不做**（单一模型）。路线图阶段二/三引入
- Persistent Memory：v4 Demo 阶段 **不做**。路线图阶段二引入（SQLite），阶段四升级（向量数据库）

**改动理由**：Demo 的第一优先级是功能正确性，不是成本优化。换模型引入的行为差异是噪音——调试时无法区分"是代码 bug 还是模型行为不同"。但路线图预留了这两个组件的升级路径，当分析师开始批量使用时（阶段三），成本控制就从"不需要"变成"关键需求"。

---

### 3.7 LangGraph — StateGraph / Checkpointer（暂不采纳）

**来源**：LangGraph 提供了 StateGraph 编排引擎，支持条件分支、子图嵌套、Human-in-the-Loop 断点重放、内置 Checkpointer。

**我们为什么暂不采纳**：
- 行业定义 Agent 的六步流程是**严格线性的**：Step 1→2→3→4→5→6，永远按固定顺序执行
- LangGraph 的核心价值（条件分支、子图、断点重放）在当前需求中为零
- 用 LangGraph 替换我们的顺序 for 循环，付出了依赖引入 + 学习成本 + 调试复杂度，换来的功能增益为零

**何时会采纳**：路线图 v2 将 LangGraph 集成放在了**附录而非阶段四必选项**，并标注了触发条件——只有当方法论演进导致步骤间出现条件分支（如"Step 3 决策后可能跳过 Step 4"）或需要非线性断点重放时，才重新评估 LangGraph 的价值。

## 四、独立设计的部分

以下设计不是在"借鉴后取舍"，而是针对本项目从零设计的：

### 4.1 六步方法论管线

**来源**：行业定义方法论文档（`方法论-v2.md`）定义的分析师工作流。

**我们做了什么**：将方法论文档中描述的分析师思维流程翻译为 Agent 可执行的六步串行管线（信息收集→维度筛选→结构决策→内容生成→自检→输出）。每一步有明确的输入、输出、方法论文档切片、验收标准。

**为什么不是借鉴**：这不是一个通用 Agent 模式——它是行业定义分析师的特定工作方法。Claude Code 和 Anthropic Harness 没有"维度筛选"或"方法论附注"的概念。

---

### 4.2 methodology_loader：按 step_id 切片注入

**来源**：项目 Brief 约束 #5 要求"方法论文档作为外部文件加载，不硬编码在 prompt 里"。

**我们做了什么**：
1. 设计了 `SLICE_MAP` 映射表，将六步的 `step_id` 映射到方法论文档中需要加载的章节关键词
2. 用正则切分 `## ` 标题，按关键词子串匹配选择相关章节
3. v4 增加了空切片降级（匹配为空时回退到全量方法论并打印警告）

**为什么不是借鉴**：Context Builder 的分层思想借鉴了 Claude Code，但"如何从一本方法论手册中为每个步骤切出正确的章节"这个具体问题，是行业定义 Agent 特有的——Claude Code 的 System Prompt 是预先定义好的静态文本，不存在"按步骤动态切片外部文档"的需求。

---

### 4.3 "做 / 打桩 / 不做"三分类框架

**来源**：从 Demo 定位（跑一次出高质量报告，不是 7×24 生产系统）出发，在架构评审中形成的项目特定的范围裁剪方法论。

**我们做了什么**：将 v2 的 9 个 Harness 组件按"对报告质量的直接影响"分为三类：
- 完整做（6 项）：直接影响报告质量的组件
- 打桩做（5 项）：保留接口但实现从简，为升级预留空间
- 不做（3 项）：Demo 阶段不需要、接口也不留

**为什么不是借鉴**：这个分类框架是评审驱动产生的——先是 v2 过度工程化（14 个文件全做完），然后 v3 做了一次激进裁剪，v4 在审查后微调。它是项目特定决策的产物，不是对某个成熟框架的照搬。

---

### 4.4 架构演进路线图的闸门机制

**来源**：针对路线图 v1 缺陷（只有"什么时候升级"，没有"什么情况下不升级"）的修复。

**我们做了什么**：每个阶段增加：
- 进入条件（闸门）：所有条件满足才进入下一阶段
- 退出条件：什么情况下不进入下一阶段（如"Demo 已满足分析师需求，不需要 Web UI"）
- 具体可验证的指标（如"3 个行业 C1-C5 通过率 ≥ 90%"）

**为什么不是借鉴**：大多数 Agent 系统的路线图只有"什么时候做"，没有"什么时候停"。这是架构评审中对 v1 "演进路线图缺少"不演进"讨论"的直接回应。

---

### 4.5 Step 5 失败时的警告注入（而非自动修正）

**来源**：项目 Brief 约束 #3（"不通过则标记，不允许直接输出"）与 Anthropic Three-Agent Harness 自动修正思想之间的权衡。

**我们做了什么**：Step 5 失败时，不自动回到 Step 4 重跑（拒绝了 Anthropic 做法），也不静默输出不合格报告（修复了 v3 的缺陷）。而是：
1. 把失败维度和问题列表注入报告头部（`## ⚠️ 自检未通过`）
2. 打印 stderr 警告
3. 继续输出（让分析师看到"这份报告审过了，但没通过，问题在哪"）

**为什么是独立设计**：这既不是 Anthropic 的全自动修正，也不是项目 Brief 的"直接不输出"——它是"带着审查痕迹输出"。这个折中方案是评审过程中产生的：既尊重了 Brief 的约束精神（不自动改），又避免了 v3 的逻辑矛盾（验收说 pass 但静默输出 fail）。

## 五、借鉴深度分级

| 层级 | 描述 | 示例 |
|------|------|------|
| **完全采纳** | 设计思想直接引入，几乎不改 | 搜索并行执行 |
| **有取舍改动** | 核心思想保留，但简化为 Demo 适配版 | Context Builder（18→4 层）、Circuit Breaker（状态机→retry）、Independent Evaluator（三 Agent→单 Agent+独立审查） |
| **打桩预留** | 接口保留完整思想，实现极简 | Session Event Log、Checkpoint Manager、Token Audit |
| **路线图预留** | Demo 不做，但在路线图中规划 | Model Router、Persistent Memory、Prompt Cache |
| **暂不采纳** | 当前需求不需要，未来可能重新评估 | LangGraph 集成 |
| **独立设计** | 项目特有，不从任何系统借鉴 | 六步管线、methodology_loader 切片、做/打桩/不做框架、闸门机制、Step 5 警告注入 |
